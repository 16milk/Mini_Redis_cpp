## 0. 这份文档是一条流水线

性能工作最常见的失败模式是「跳步」：凭直觉猜一个瓶颈（通常是「epoll 不够快，换 io_uring」），改完之后既说不清收益来自哪里，也不知道有没有引入新的退化。

本文把网络性能工作拆成六个必须按顺序走的阶段，每一阶段都有明确的**入口条件**和**出口产物**：

~~~text
  阶段一  建立基线          没有基线，"变快了"是无法证伪的说法
     |     出口：固定环境 + 固定 workload + 一组可复现数字
     v
  阶段二  发现异常          看四类信号，而不是看单一 QPS 数字
     |     出口：一条"症状"描述，例如 "pipeline 加深时吞吐反而下降"
     v
  阶段三  定位到代码        把症状收敛到函数与代码行
     |     出口：可疑代码清单 + 每一项的因果假设
     v
  阶段四  量化与归因        证明这行代码就是主因，并给出量级
     |     出口：对照实验数据 + 复杂度判据
     v
  阶段五  实施修复          一次只改一类问题，保持语义不变
     |     出口：可独立 review 的提交序列
     v
  阶段六  验证与防回归      把本次结论固化成自动化断言
        出口：CI 中的复杂度回归测试 + 性能门槛
~~~

第 2–4 章讲**怎么发现**（方法论 + 本轮真实执行过程），第 5–7 章讲**发现了什么**（瓶颈清单），第 8 章讲**怎么解决**（逐个给方案和代码），第 9–10 章讲**怎么验证**和**提交拆分**。

## 1. 执行摘要

### 1.1 一句话结论

**继续保留 epoll。当前最大的瓶颈不在 I/O 模型，而在两处用户态的二次复杂度算法；实测修掉第一处即可获得 700 倍级的热路径改善。**

### 1.2 上一版之后已经解决的问题

上一版把「无预算、无背压、写缓冲头删」列为 P0。这些在 `c3a963b` 中已经实现，本文确认如下：

| 上一版 P0/P1 问题 | 当前状态 | 代码证据 |
| --- | --- | --- |
| 单连接单轮工作无预算 | **已解决**：读字节/读次数/命令数/命令时间/写字节/写次数六项预算 | `Server.cpp:28-37` |
| 缺少本地 ready queue | **已解决**：`ready_clients_` + `enqueue_client` + 有界轮次 | `Server.cpp:214-247`、`Server.hpp:59-61` |

这是一次质量很高的迭代，事件循环的**调度骨架**已经正确了。因此本文不再重复这些内容。

### 1.3 本轮新发现 / 仍未解决的问题

| 编号 | 瓶颈 | 实测量级 | 性质 |
| --- | --- | --- | --- |
| **B1** | 读缓冲区每条命令 `erase(0, n)` 头删 | **704×**（80k 命令 pipeline） | 二次复杂度，吞吐 |
| **B2** | 不完整帧每轮从 offset 0 重新解析并重复复制参数 | **31× 参数复制放大** | 二次复杂度，CPU 放大 |
| **B3** | `accept` 遇 `EMFILE` 在水平触发下活锁 | 100% CPU + 无界日志 | 可用性，可被触发 |
| **B4** | 每轮无条件 `EPOLL_CTL_MOD` + 单发 accept + 冗余 read | 小命令路径 25% syscall 是纯浪费 | 控制面开销 |
| **B5** | 请求 >1 MiB 被静默关闭连接，无协议错误回复 | 功能缺陷 | 语义正确性 |
| **B6** | `encodeArray` 无 reserve；`sendResponse` 只有 const& 重载 | **2.5×** / **2.1–2.5×** | 分配与复制 |
| **B7** | 每次连接/断开 `std::endl` 同步 flush | 短连接风暴串行点 | 尾延迟 |
| **B8** | 预算、水位、backlog、批量全为编译期常量 | 无法压测调参 | 可运维性 |
| **B9** | `SAVE` / `KEYS` 同步跑在事件线程 | 全连接 stall | 尾延迟 |

B1、B2 是「先解决这两个，其他再谈」级别的问题。B3 是一个可用性缺陷，优先级等同 bug。

### 1.4 路线判断

- **P0**：修 B1、B2、B3。B1/B2 是纯算法改造，语义不变，收益已被实测证明。
- **P1**：修 B4–B8。低风险，主要降低 syscall 与分配。
- **P2**：处理 B9，需要先定义快照语义。
- **P3**：多 Reactor —— 只有在 Linux 基线证明单 I/O 线程饱和后才做。
- **P4**：io_uring —— 只作为可回退的 A/B 实验后端，准入条件见第 11 章。

**现在切 io_uring 一定是错的选择**：B1 是 704 倍的算法问题，io_uring 优化的是 syscall 提交开销。用一个高复杂度的 I/O 后端去改善一个被 `memmove` 主导的热路径，收益会被完全掩盖。

## 2. 阶段一：建立可复现基线

### 2.1 为什么这一步不能跳

没有基线，后面每一个阶段都无法执行：

- 无法**发现**异常 —— 「30 万 QPS」是好还是坏？不知道。
- 无法**归因** —— 改了三处，快了 20%，是哪一处贡献的？不知道。
- 无法**验证** —— 修复引入的内存增长要到线上才暴露。

基线的本质不是「一个漂亮的数字」，而是「一组在同环境、同版本工具下可重复的数字」。**相对变化才是结论，绝对数字只是上下文。**

### 2.2 当前仓库的基线设施缺口

这是需要优先补齐的：

- `CMakeLists.txt` 中没有任何 benchmark target。
- `tests/NetworkIoTest.cpp` 与 `tests/MultiClientIoTest.cpp` 使用 `AF_UNIX socketpair`，**完全绕过** `listen`/`accept`/`epoll`/真实 TCP。它们验证的是 `Connection` 与协议层语义，不是服务端性能。
- 没有历史结果存档，没有回归阈值，没有环境元数据记录。

### 2.3 固定构建与环境

### 2.4 workload 集合

本项目只接受 RESP 数组格式（`Protocol.cpp:63-65`：首字节非 `*` 直接返回 `ERROR`），**不支持 inline command**。因此不能直接用 `redis-benchmark` 默认测试组，因为它包含 `PING_INLINE`，会全部失败。必须用末尾指定命令的形式：

```bash
BENCH="redis-benchmark -h 127.0.0.1 -p 6379"

# A. 单连接无 pipeline：最小路径延迟，暴露每请求固定开销（syscall、分配）
$BENCH -n 100000  -c 1  -P 1   PING
$BENCH -n 100000  -c 1  -P 1   -t set,get

# B. 多连接无 pipeline：暴露调度、accept、epoll 控制面行为
$BENCH -n 1000000 -c 50 -P 1   PING
$BENCH -n 1000000 -c 50 -P 1   -t set,get

# C. 多连接 + pipeline：放大缓冲区管理与解析热点（B1 在这里暴露）
$BENCH -n 1000000 -c 50 -P 16  PING
$BENCH -n 1000000 -c 50 -P 128 PING
$BENCH -n 1000000 -c 50 -P 128 -t set,get

# D. 大 value：暴露 read/send 次数、分配与内存带宽
$BENCH -n 100000  -c 50 -P 16  -t set,get -d 65536

# E. 连接风暴：暴露 B3、B4、B7
for i in $(seq 1 2000); do (exec 3<>/dev/tcp/127.0.0.1/6379; exec 3<&-) & done; wait
```

### 2.5 仓库内需要补的场景驱动器

`redis-benchmark` 测不了故障与公平性场景，这些必须自己写：

- **慢读客户端**：只发不收，验证输出背压在 4 MiB 处生效且 RSS 有界。
- **永不完整的巨型请求**：声明大 bulk 后缓慢发送，验证输入上限（当前会触发 B5）。
- **公平性混合**：1 个 `-P 1024` 深 pipeline 客户端 + 50 个普通客户端，测普通客户端 p99。
- **fd 耗尽**：`ulimit -n 64` 后发起 200 连接，验证 B3。
- **持久化干扰**：`SAVE` / `KEYS *` 与普通 `GET` 并发，量化 event-loop stall。
- **soak**：1 小时以上，观察 RSS、fd 数、连接状态是否稳定。

### 2.6 每轮必须记录的指标

| 类别 | 指标 |
| --- | --- |
| 吞吐 | requests/s、commands/s |
| 延迟 | p50、p95、p99、**p99.9**、max |

## 3. 阶段二：发现异常 —— 四类信号与分诊表

不要盯着单一 QPS 数字。要看**四类信号**，因为不同瓶颈在这四类信号上留下的指纹完全不同。这张表就是「从现象猜方向」的分诊工具：

| 信号 | 观察到的现象 | 高概率原因 | 下一步动作 |
| --- | --- | --- | --- |
| **S1 吞吐不随 pipeline 深度提升，甚至倒退** | `-P 128` 的 QPS ≤ `-P 16` | 缓冲区管理是超线性的（B1）；或单轮预算过小导致来回调度 | 做 2× 标定实验（§4.2） |
| **S1'吞吐不随连接数提升** | `-c 200` ≈ `-c 50`，且单核已满 | 单线程 CPU 上限；或存在串行点（B7） | 看 user/sys 拆分 |
| **S2 p99/p99.9 与 p50 严重分叉** | p50 = 0.2 ms，p99.9 = 80 ms | 事件循环长任务：同步 `SAVE`/`KEYS`（B9）；单连接独占（已由预算缓解）；日志 flush（B7） | 埋 event-loop stall 直方图 |
| **S3 RSS 持续增长或不回落** | 慢客户端场景下 RSS 单调上升 | 输入/输出缓冲无上限；或 compact 阈值失效 | 打印每连接 pending 字节 |
| **S4 CPU 结构异常** | **user% 远高于 sys%** | 用户态热点：memmove、解析、分配（B1/B2/B6） | perf record → 火焰图 |
| | **sys% 占比高** | syscall 过多：冗余 `epoll_ctl`、单发 accept、多余 read（B4） | `strace -c` 数 syscall |
| | **两者都不高但 QPS 低** | 在等待：磁盘 fsync（B9）、锁、或客户端本身是瓶颈 | 先确认压测端不是瓶颈 |

### 3.1 关键判读原则

1. **先排除测试端瓶颈**。`redis-benchmark` 单进程也会打满一个核。服务端 CPU 未满而 QPS 不涨时，先确认客户端不是瓶颈。
2. **user vs sys 是第一个分岔口**。它决定你是去看火焰图（user 高）还是去数 syscall（sys 高）。本项目的判断是 **user 主导**，因为 B1/B2 是纯用户态的内存搬移与复制。
3. **p99.9 比平均值更有信息量**。平均延迟会把 event-loop stall 完全平滑掉；一次 200 ms 的 `SAVE` 在 100 万请求里对均值几乎无影响，但会精确出现在 p99.9 和 max 上。
4. **单调性本身就是证据**。「加深 pipeline 反而变慢」在设计上不该发生 —— pipeline 的全部意义就是摊薄 syscall。一旦观察到倒退，几乎可以直接锁定缓冲区管理的复杂度问题。

## 4. 阶段三 + 四：定位到代码，并量化归因

### 4.1 本轮实际采用的定位方法及其边界

**必须先说明约束**：分析主机是 macOS arm64，而 `Server.cpp` 直接 `#include <sys/epoll.h>`，因此**无法在本机启动真实 Server**，也就无法执行 §2.4 的 Linux 压测、`perf` 和 `strace`。

在这个约束下，仍然可以做两件有决定性的事：

1. **复杂度标定（scaling test）**：把用户态热路径从服务端剥离出来，用同一段真实项目代码（`src/net/Protocol.cpp` 直接参与编译）在成倍增长的输入规模上测耗时。复杂度是算法性质，**与操作系统和 I/O 模型无关**，因此这类结论可以跨平台成立。
2. **对照实验（A/B）**：同一 workload 下，只替换待验证的那一处策略，其余完全相同。这样得到的比值就是该处策略的贡献，而不是混合收益。

**判据**：输入规模翻倍时，
- `T(2N)/T(N) ≈ 2` → 线性，健康；
- `T(2N)/T(N) ≈ 4` → **二次复杂度**，存在按规模放大的搬移或重复扫描。

这个判据的好处是它不依赖绝对性能，因此**在任何机器上都成立**，非常适合放进 CI（见 §10.3）。

**这些结论不能替代什么**：不能证明真实 TCP 吞吐、accept 行为、epoll 关注集切换成本、多连接公平性和尾延迟。所有绝对收益必须在 Linux 上复测。

### 4.2 实验一：读缓冲消费策略（定位 B1）

**假设**：`Connection::consumeInput` 每解析完一条命令就从 `read_buffer_` 头部 `erase`，导致剩余数据被反复 `memmove`。

现状代码：

```118:124:src/net/Connection.cpp
void Connection::consumeInput(size_t n) {
    if (n >= read_buffer_.size()) {
        read_buffer_.clear();
    } else {
        read_buffer_.erase(0, n);
    }
}
```

配合 `Server.cpp:182-183`，解析**永远从索引 0 开始**：

```180:184:src/net/Server.cpp
        std::vector<std::string> arguments;
        std::size_t bytes_consumed = 0;
        const auto result =
            parser.parse(connection.getReadBuffer(), arguments, bytes_consumed);
```

对照组是「游标推进 + 阈值集中 compact」。结果（每组 7 次取中位数，`PING` pipeline）：

| pipeline 命令数 | 现状 `erase`(ms) | 游标(ms) | 加速比 | 规模翻倍时的耗时倍数（现状 / 游标） |
| ---: | ---: | ---: | ---: | :--- |
| 1,000 | 0.211 | 0.022 | 9.8× | — |
| 5,000 | 1.659 | 0.068 | 24.5× | 7.86 / 3.14 |
| 10,000 | 8.105 | 0.152 | 53.4× | 4.89 / 2.24 |
| 20,000 | 35.745 | 0.245 | 146.2× | 4.41 / 1.61 |
| 40,000 | 152.812 | 0.499 | 306.2× | 4.28 / 2.04 |
| 80,000 | 622.762 | 0.997 | **624.6×** | **4.08 / 2.00** |

**结论**：现状的翻倍倍数稳定收敛到 **4.08**，是教科书级的二次复杂度；游标版收敛到 **2.00**，是精确的线性。假设成立。

### 4.3 实验一 b：归因 —— 到底是 `erase` 还是参数复制？

上面的对照组同时改了两件事（游标 + `string_view` 参数），所以 624× 是混合收益，**不能直接归因给 `erase`**。必须再做一次隔离实验：两组都构造 `vector<std::string>`（即都保留参数复制），**只有消费策略不同**。

workload 改为更真实的 `GET` + 32 字节参数：

| pipeline 命令数 | `erase`(ms) | 游标(ms) | 加速比 |
| ---: | ---: | ---: | ---: |
| 5,000 | 13.026 | 0.273 | 47.7× |
| 20,000 | 144.309 | 0.814 | 177.2× |
| 80,000 | 2380.724 | 3.380 | **704.3×** |

**归因结论**：**704× 全部来自消费策略本身**，与参数是否用 `string_view` 无关。这个结果直接决定了修复顺序：

> **先把 `erase` 改成游标（低风险、纯算法、语义不变、收益 704×），再谈 `string_view`（有生命周期风险、收益是剩下的零头）。**

这正是「量化归因」阶段存在的意义 —— 如果跳过它，很可能会先去做那个风险高得多、收益小得多的 `string_view` 改造。

### 4.4 实验二：不完整帧的重解析放大（定位 B2）

**假设**：`parse` 是无状态的且总是从头开始。当一个多参数命令跨多轮到达时，每一轮都会重新扫描并**重新复制所有已到达的参数**，然后在返回 `INCOMPLETE` 时把它们全部丢弃。

代码依据 —— `parse` 在 `INCOMPLETE` 前已经执行了 `args.emplace_back(input.substr(...))`：

```109:118:src/net/Protocol.cpp
        const auto bulk_length = static_cast<size_t>(length);
        if (bulk_length > input.size() - pos) {
            return ParseResult::INCOMPLETE;
        }
        if (input.size() - pos - bulk_length < 2) {
            return ParseResult::INCOMPLETE;
        }

        args.emplace_back(input.substr(pos, bulk_length));
```

即：前 k 个参数已完整到达、第 k+1 个未到达时，前 k 个参数的 `substr` 复制**已经全部发生**，然后整个 `args` 被丢弃。

实验：单条多参数命令以 16 KiB 分片到达（模拟每轮读预算），统计总参数复制次数：

| 帧大小 | 参数个数 | 总耗时(ms) | 实际参数复制次数 | 放大倍数 |
| ---: | ---: | ---: | ---: | ---: |
| 60.6 KiB | 2,000 | 0.116 | 5,169 | 2.6× |
| 242.2 KiB | 8,000 | 1.589 | 71,410 | 8.9× |
| 968.8 KiB | 32,000 | 22.913 | **999,140** | **31.2×** |

**结论**：放大倍数 ≈ 分片轮数 / 2，同样是二次增长。一条约 1 MiB、32,000 参数的命令会产生近 **100 万次**字符串分配与复制，其中 96.8% 是纯浪费的 22.9 ms CPU。

这里有两层危害：

1. **性能**：`MSET`、`DEL`、`SADD` 这类多参数命令在慢速网络或大参数下必然跨轮到达，直接吃到这个放大。
2. **可被恶意触发**：客户端只要以小分片持续投喂一个大的多参数帧，就能让服务端在**单核上**做二次复杂度的无效分配。由于当前输入上限是 1 MiB，单次被限制在上述量级，但客户端可以反复进行。

### 5.1 关于水位设置的一处观察

当前 `EPOLLIN` 的暂停与恢复在输出侧**共用同一个阈值** `kOutputResumeWatermark`（2 MiB，见 `Server.cpp:144`），没有迟滞区间，在该点附近可能反复 `EPOLL_CTL_MOD` 抖动。输入侧则是正确的：暂停用 1 MiB、恢复用 512 KiB。

## 6. 阶段五：逐个解决

每一项的结构是：根因 → 方案 → 代码 → 风险 → 验收。

### 6.1 B1：读缓冲改为游标 + 摊还 compact 【P0】

**根因**：`std::string::erase(0, n)` 必须把后续全部字节前移。N 条命令的 pipeline 产生 N 次搬移，总搬移量 ~N²/2。

**方案**：`Connection` 增加 `read_offset_`，消费只推进游标；只有当已消费前缀既超过绝对阈值、又占缓冲一半以上时，才做一次集中 compact。

**为什么这样能摊还到 O(1)/字节**：compact 的触发条件是「已消费 ≥ 剩余」，所以每次 compact 搬移的字节数不超过此前已消费的字节数；要再次触发就必须再消费同样多的量。因此总搬移量与总字节数成线性关系。绝对阈值（64 KiB）用来避免小缓冲上的高频小 compact。

```cpp
// include/mini_redis/net/Connection.hpp
class Connection {
public:
    // 返回未消费区间的视图。注意：任何 readFromSocket() 或 consumeInput()
    // 都可能使之前返回的视图失效，调用方必须每轮重新获取。
    std::string_view input() const {
        return std::string_view(read_buffer_.data() + read_offset_,
                                read_buffer_.size() - read_offset_);
    }

    bool hasPendingInput() const { return read_offset_ < read_buffer_.size(); }
    std::size_t pendingInputBytes() const { return read_buffer_.size() - read_offset_; }

    void consumeInput(std::size_t n);
    void discardInput() {
        read_buffer_.clear();
        read_offset_ = 0;
        needed_input_bytes_ = 0;   // 供 B2 使用
    }

private:
    std::string read_buffer_;
    std::size_t read_offset_ = 0;
};
```

```cpp
// src/net/Connection.cpp
void Connection::consumeInput(std::size_t n) {
    read_offset_ = std::min(read_offset_ + n, read_buffer_.size());

    // 全部消费完是最常见情况：直接清空，游标归零，且不发生搬移。
    if (read_offset_ == read_buffer_.size()) {
        read_buffer_.clear();
        read_offset_ = 0;
        return;
    }

    // 摊还 compact：已消费前缀同时超过绝对阈值且占比过半时才搬移一次。
    constexpr std::size_t kCompactThreshold = 64 * 1024;
    if (read_offset_ >= kCompactThreshold &&
        read_offset_ >= read_buffer_.size() / 2) {
        read_buffer_.erase(0, read_offset_);
        read_offset_ = 0;
    }
}
```

`Protocol.hpp` 的 `parse` 改为接受 `std::string_view`：

```cpp

                  size_t& bytes_consumed) const;
```

实现内部逻辑不变，只需把 `input.substr(pos, blen)` 的结果显式构造为 `std::string`（`args` 仍是 `vector<std::string>`）。

`Server::process_client_input` 相应改为：

```cpp

```

**风险**：
- `std::string_view` 生命周期。`readFromSocket` 的 `append` 可能触发扩容，`consumeInput` 的 compact 会搬移数据，两者都会使旧视图失效。约束：**视图不得跨越这两个调用存活**。当前 `process_client_input` 的循环每轮重新调用 `connection.input()`，满足该约束。
- 现有 `getReadBuffer()` 返回 `const std::string&`，被 `tests/NetworkIoTest.cpp` 等使用。建议一次性替换为 `input()`，避免留下一个语义已变（含已消费前缀）的旧接口。
- `pendingInputBytes()` 语义必须同步改为「未消费字节数」，否则 `Server.cpp` 中所有输入水位判断都会因为把已消费前缀算进来而提前触发。**这是本次改造最容易出错的一点。**

**注意**：本阶段**刻意不把 `args` 改成 `string_view`**。§4.3 已证明 704× 与此无关，而 `string_view` 参数会把生命周期约束一路传播到 `CommandHandler` 和 `Database`，风险不成比例。

**验收**：`T(2N)/T(N)` 从 4.08 降到接近 2.0（见 §10.3 的自动化断言）。

### 6.2 B2：帧扫描与解析检查点 【P0】

**根因**：两个缺陷叠加 —— (a) 解析无状态，每轮从头重扫；(b) `INCOMPLETE` 之前就已经复制了参数，随后全部丢弃。

**方案**：分离「探测帧边界」和「构造参数」两件事。

1. 新增 `scanFrame(view)`：只走 header，**不做任何分配**，返回帧长度，或在不完整时返回「至少还需要多少字节」的下界。
2. `Connection` 记住这个下界 `needed_input_bytes_`。字节数不足时**完全跳过解析**。
3. 只有确认帧完整后，才调用 `parse` 构造 `args`。

这样把「每轮 O(已到达参数数) 次分配」降为「每轮 O(1)」，参数复制总次数从 999,140 降到 32,000（即每个参数恰好一次）。

```cpp
// include/mini_redis/net/Protocol.hpp
struct FrameScan {
    enum Status { INCOMPLETE, COMPLETE, ERROR };
    Status status = INCOMPLETE;
    std::size_t frame_bytes = 0;    // COMPLETE 时：整帧长度
    std::size_t need_at_least = 0;  // INCOMPLETE 时：整帧长度的已知下界
};

// 只扫描 RESP 帧结构，不复制任何 bulk 内容。
static FrameScan scanFrame(std::string_view input);
```

`scanFrame` 的关键点：遇到 bulk header 时，即使 body 尚未到达，也**已经知道**该 body 占 `len + 2` 字节，因此可以把这些字节累加进 `need_at_least`：

```cpp
// src/net/Protocol.cpp（要点）
FrameScan RespParser::scanFrame(std::string_view in) {
    FrameScan out;
    std::size_t pos = 0;
    if (in.empty()) { out.need_at_least = 1; return out; }
    if (in[0] != '*') { out.status = FrameScan::ERROR; return out; }

    std::size_t end = in.find("\r\n", pos);
    if (end == std::string_view::npos) { out.need_at_least = in.size() + 1; return out; }

    long long argc = 0;
    if (!parseInteger(in, pos + 1, end, argc) || argc < 0 || argc > kMaxArgc) {
        out.status = FrameScan::ERROR;
        return out;
    }
    pos = end + 2;
    if (argc == 0) { out.status = FrameScan::COMPLETE; out.frame_bytes = pos; return out; }

    for (long long i = 0; i < argc; ++i) {
        if (pos >= in.size()) { out.need_at_least = pos + 1; return out; }
        if (in[pos] != '$') { out.status = FrameScan::ERROR; return out; }
        end = in.find("\r\n", pos);
        if (end == std::string_view::npos) { out.need_at_least = in.size() + 1; return out; }

        long long len = 0;
        if (!parseInteger(in, pos + 1, end, len) || len < -1 || len > kMaxBulkLen) {
            out.status = FrameScan::ERROR;
            return out;
        }
        pos = end + 2;
        if (len == -1) continue;

        const std::size_t body = static_cast<std::size_t>(len) + 2;
        if (in.size() - pos < body) {
            // body 长度已知，可以给出精确下界，避免下一轮的无效扫描。
            out.need_at_least = pos + body;
            return out;
        }
        pos += body;
    }
    out.status = FrameScan::COMPLETE;
    out.frame_bytes = pos;
    return out;
}
```

`Server::process_client_input` 变成两段式：

```cpp
while (connection.hasPendingInput()) {

    // 已知还差多少字节时直接返回，连扫描都不做。
    if (connection.pendingInputBytes() < connection.neededInputBytes()) {
        return outcome;
    }

    const auto scan = RespParser::scanFrame(connection.input());
    if (scan.status == FrameScan::INCOMPLETE) {
        connection.setNeededInputBytes(scan.need_at_least);
        if (connection.peerReadClosed()) { /* 与现状一致：回错误并关闭 */ }
        return outcome;
    }
    if (scan.status == FrameScan::ERROR) { /* 与现状一致 */ }

    // 帧已完整，此时才做唯一一次参数构造。
    connection.setNeededInputBytes(0);
    std::vector<std::string> arguments;
    std::size_t bytes_consumed = 0;
    parser.parse(connection.input().substr(0, scan.frame_bytes),
                 arguments, bytes_consumed);
    connection.sendResponse(command_handler_.execute(arguments));
    connection.consumeInput(scan.frame_bytes);
    ++outcome.commands_processed;
    // ...输出水位检查不变...
}
```

**风险**：
- `scanFrame` 与 `parse` 的语法判定必须**完全一致**，否则会出现「扫描说完整、解析说不完整」的死循环。**必须写针对性测试**：对同一批输入（含所有截断位置）断言两者结论一致。这是本改造唯一的真实风险点。
- `needed_input_bytes_` 必须在 `consumeInput`、`discardInput` 和协议错误路径上正确清零，否则连接会永久停止处理输入。

**验收**：§4.4 的参数复制次数从 999,140 降到 32,000；耗时从 22.9 ms 降到亚毫秒级。

### 6.3 B3：修复 `EMFILE` 活锁并引入连接上限 【P0】

**根因**：这是本文唯一的**可用性缺陷**，值得单独说明因果链：

```99:106:src/net/Server.cpp
    const int client_fd = accept(
        listen_fd_, reinterpret_cast<struct sockaddr*>(&client_addr), &client_len);
    if (client_fd == -1) {
        if (errno != EAGAIN && errno != EWOULDBLOCK && errno != EINTR) {
            std::cerr << "[WARN] accept failed: " << std::strerror(errno) << std::endl;
        }
        return;
    }
```

当进程 fd 用尽时，`accept` 返回 `EMFILE`。此时：

1. 待接受的连接**仍然留在 accept 队列中**，没有被取走；
2. 监听 socket 是**水平触发**的，因此它依然「可读」；
3. 下一次 `epoll_wait` **立即**返回（`Server.cpp:406`）；
4. 再次 `accept` → 再次 `EMFILE` → 再写一行带 flush 的 `stderr`；
5. 回到第 2 步。

结果是**紧凑的忙循环**：单核 100% CPU、无界 stderr 输出、所有已建立连接因为得不到调度而全部停摆。由于当前**没有任何 max clients 限制**（`Server.cpp:128` 无条件 `emplace`），在默认 `ulimit -n 1024` 下，约 1000 个并发连接就能触发。

**方案**（三层，缺一不可）：

```cpp
// 1) 应用层上限：在 fd 耗尽之前就主动拒绝，这是常规路径。
//    仍然 accept 取走连接（否则 LT 会立刻再次触发），回错误后关闭。
if (connections_.size() >= config_.max_clients) {
    const char* msg = "-ERR max number of clients reached\r\n";
    ::send(client_fd, msg, std::strlen(msg), MSG_NOSIGNAL | MSG_DONTWAIT);
    ::close(client_fd);
    ++stats_.rejected_max_clients;
    continue;   // 继续排空 backlog，而不是让它堆积
}
```

```cpp
// 2) EMFILE/ENFILE 兜底：即使低于 max_clients 也可能发生（RDB 文件、epoll fd 等）。
//    必须摘掉监听 fd 的 EPOLLIN，否则 LT 必然活锁。
if (client_fd == -1) {
    if (errno == EAGAIN || errno == EWOULDBLOCK) break;   // backlog 排空，正常退出
    if (errno == EINTR) continue;
    if (errno == ECONNABORTED) continue;                  // 客户端在 accept 前就断开
    if (errno == EMFILE || errno == ENFILE) {
        pause_accept();          // EPOLL_CTL_MOD 去掉 EPOLLIN
        accept_paused_ = true;
        log_rate_limited("accept: fd exhausted, pausing acceptor");
        break;
    }
    log_rate_limited("accept failed");
    break;
}
```

```cpp
// 3) 恢复路径：任何客户端关闭都可能释放出 fd。
void Server::close_client(int fd) {
    // ...现有清理逻辑...
    if (accept_paused_) {
        resume_accept();         // EPOLL_CTL_MOD 加回 EPOLLIN
        accept_paused_ = false;
    }
}
```

另外，`epoll_timeout_ms` 在 `accept_paused_` 时必须返回一个**有界**超时（例如 100 ms），否则在「没有任何客户端活动、也没有过期任务」的情况下，acceptor 可能永久挂起。

**配套**：启动时读取 `RLIMIT_NOFILE`，并把 `max_clients` 设为 `rlimit - 保留量`（保留给监听 fd、epoll fd、RDB 临时文件、目录 fsync fd、stdio）。若 `rlimit` 过低则直接在启动时告警，而不是等到运行时才暴露。

**验收**：`ulimit -n 64` 下发起 200 连接 —— CPU 不应达到 100%，已建立连接必须继续正常响应，被拒绝的客户端应收到明确错误，日志条数必须有界。

### 6.4 B4：削减控制面 syscall 【P1】

#### (a) 缓存 interest mask，值不变就不发 syscall

```cpp
    const std::uint32_t desired = compute_interest(connection);
```

务必在 `EPOLL_CTL_ADD` 成功后同步初始化 `setEpollInterest(EPOLLIN | EPOLLRDHUP)`，否则第一次 MOD 会被错误地跳过。

#### (b) `accept4` 批量接收

#### (c) 短读提前退出

```cpp
// Connection::readFromSocket 循环内

    read_buffer_.append(buf, static_cast<std::size_t>(read_count));
    result.bytes_read += static_cast<std::size_t>(read_count);

```

正确性论证：短读**不保证** socket 此刻为空（数据可能在两次调用之间到达）。但在 LT 下这不会丢事件 —— 只要还有数据可读，`epoll_wait` 就会再次报告该 fd。注意此路径必须让 `budget_exhausted` 保持 `false`（短读不是预算耗尽），否则会产生无意义的 requeue。

#### (d) 输出侧水位拆分

按 §5.1，把 `EPOLLIN` 暂停阈值改为 `kOutputHighWatermark`、恢复阈值改为 `kOutputResumeWatermark`，与输入侧对称，形成真正的迟滞区间。

**验收**：`strace -c -f` 下每请求 `epoll_ctl` 次数趋近 0；每连接建立 syscall 从 5 降到 2；`-c 50 -P 1` 场景 sys CPU 占比明显下降。

### 6.5 B5：显式协议限制与正确的错误回复 【P1】

**根因**：`kInputHighWatermark`（1 MiB）实际上成了**隐式的最大请求大小**，且超限处理是「记一行日志然后关闭连接」：

```326:333:src/net/Server.cpp
        if (connection.pendingInputBytes() >= kInputHighWatermark &&
            output_allows_commands &&
            !input_result.needs_more_processing) {
            std::cout << "[INFO] Client input buffer limit exceeded, fd="
                      << fd << std::endl;
            close_client(fd);
            continue;
        }
```

后果：一个合法的 1 MiB `SET` 会导致连接被静默断开，客户端只看到「连接重置」，无法区分「服务端 bug」「网络故障」还是「超出限制」。同时 `Protocol.cpp:73-75` 允许 `argc` 高达 `INT_MAX`，没有项目级上限。

**方案**：把「协议合法性上限」与「缓冲区容量上限」分成两个独立概念，对齐 Redis 的做法：

| 限制 | 建议值 | 超限行为 |
| --- | --- | --- |
| `max_argc` | 1024 × 1024 | 回 `-ERR Protocol error: invalid multibulk length`，关闭 |
| `max_bulk_len` | 512 MiB（对齐 `proto-max-bulk-len`） | 回 `-ERR Protocol error: invalid bulk length`，关闭 |
| `max_query_buffer` | 应显著大于 `max_bulk_len` | 回 `-ERR Closing client that reached max query buffer length`，关闭 |
| `max_frame_bytes` | 项目自选（如 64 MiB） | 同上 |

关键要求：**必须先把错误响应写出去，再关闭连接**。项目中已有 `close_after_write_` 机制正是为此设计的，直接复用即可 —— 不要用 `close_client` 直接断开。

这些上限在 `scanFrame` 中检查（见 §6.2 的 `kMaxArgc` / `kMaxBulkLen`），可以在参数被分配之前就拒绝畸形帧，这本身也是一层防护。

### 6.6 B6：减少响应编码的分配与复制 【P1】

```cpp

        out += "\r\n";
```

`sendResponse` 增加右值重载：



### 6.7 B7：连接日志治理 【P1】

`std::endl` 每次都触发 flush，即每条日志一次 `write` syscall。当前每个连接生命周期至少产生 2 条（connect + disconnect），短连接风暴下这是事件循环上的同步串行点。

方案：
- 引入日志级别，把每连接的 connect/disconnect 降到 `DEBUG`，默认关闭。
- 热路径统一用 `'\n'`，不用 `std::endl`。
- 错误日志做**频率限制**（这也是 §6.3 活锁修复的必要组成部分）。
- 用计数器代替逐事件日志：`connections_accepted`、`connections_closed`、`rejected_max_clients`、`protocol_errors` 等，通过 `INFO` 类命令暴露。

### 6.9 B9：把持久化和长命令移出事件循环 【P2】

**根因**：`SAVE` 在事件线程内完成「全量编码 → 写临时文件 → `fsync` 文件 → `rename` → `fsync` 父目录」（`Rdb.cpp:886-927`）。整个过程中服务端不 accept、不 read、不 write。`fsync` 的尾延迟可达数百毫秒甚至更久，这会直接、完整地出现在所有客户端的 p99.9 上。`KEYS` 同样是线性遍历 + 构造完整数组响应的长任务。

**不能简单丢进线程池**：`Database` 及其内部对象是可变且无锁的，后台线程直接遍历会与命令写入产生数据竞争，也无法保证快照一致性。

按代价从低到高的可选方案：

1. **最小改造（先做这个）**：保留同步 `SAVE`，但增加 event-loop stall 指标，把它明确标注为「非在线低延迟路径」。**先量化再优化** —— 这条本身就是有价值的交付。
2. **`KEYS` → `SCAN`**：引入游标式命令，把一次长遍历拆成多次有界调用。这是收益最确定、语义最清晰的一步，且与现有的 `commands_per_turn` 预算天然契合。
3. **fork + COW（类 `BGSAVE`）**：Linux 优先方案，与 Redis 一致。前置要求是所有 fd 都带 `CLOEXEC`（见 §6.4b），并需处理子进程回收、失败上报和并发 `BGSAVE` 抑制。
4. **不可变快照 / 版本化视图**：跨平台方案，但需要 `Database` 支持写时复制。仓库中已有 `docs/读写并发、写时复制与锁设计.md`，应与之统一设计而不是另起一套。

## 7. 保持不变的部分

优化时必须保留这些已经正确的行为，任何改动都不能破坏它们：

- 监听 socket 与客户端 socket 均为非阻塞。
- 读循环正确区分 EOF、`EINTR`、`EAGAIN` 和真实错误。
- `send` 使用 `MSG_NOSIGNAL`，避免对端关闭导致 `SIGPIPE` 终止进程。
- 部分写后保留剩余响应，并按需订阅 `EPOLLOUT`（而非常开，避免忙循环）。
- 对端半关闭后，仍把已排队的响应发送完成。
- 单连接内响应顺序与请求顺序严格一致。
- 协议错误后不再信任帧边界，丢弃剩余输入并在写完错误响应后关闭。
- 事件循环每轮都给过期维护一个有界时间片，且 `epoll_wait` 超时会考虑下一个过期时间。

**特别地：不建议为了「看起来更高性能」而切换到 `EPOLLET`。** LT 是当前预算调度与背压设计的前提 —— §6.4c 的短读提前退出、§6.3 的 acceptor 暂停/恢复、以及未读尽 socket 的自动重新通知，都依赖 LT 语义。切到 ET 需要额外的显式重调度或 `EPOLLONESHOT` rearm，否则容易把未处理的工作永久卡住。是否切换应由真实的 wakeup 数据决定，而不是先验偏好。

## 10. 阶段六：验证与防回归

### 10.1 正确性与资源安全

- 现有 pipeline、分片输入、部分写、半关闭、多客户端测试继续通过。
- 新增真实 TCP/epoll 集成测试：响应内容与单连接顺序**零变化**。
- 任意不完整请求不能让单连接输入超过配置硬上限。
- 慢读客户端不能让单连接输出超过配置硬上限，RSS 必须有界。
- 超限请求收到**明确的协议错误响应**，而不是被静默断开（B5 验收）。
- 水位切换不产生忙循环，也不会把已完整的请求永久卡住。
- `fd` 耗尽时不活锁，已建立连接继续可用（B3 验收）。
- 连接关闭、fd 复用、epoll ADD/MOD 失败路径无 double-close 与 use-after-free。
- ASan / UBSan 通过；若进入多 Reactor 阶段，追加 TSan。

### 10.2 算法与调度

- pipeline 处理从二次退化变为近线性（见 10.3）。
- §4.4 的参数复制次数从 999,140 降到约 32,000。
- 单次事件处理不超过配置的命令/字节预算。
- accept 队列在一次或少量批次内排空，而不是每事件仅取一个。
- 关注集未变时不调用 `EPOLL_CTL_MOD`；用 `epoll_mod_calls` 计数器验证降幅。
- 存在深 pipeline 客户端时，普通客户端 p99 有明确上界，不随 pipeline 深度无界放大。

### 10.3 把本次结论固化为 CI 断言（关键）

这是本文最重要的可交付项之一：**把「怎么发现」这件事自动化**，让同类退化在未来无法悄悄回来。

复杂度断言不依赖绝对性能，因此在任何机器、任何 CI runner 上都稳定：

```cpp
// tests/ScalingRegressionTest.cpp（要点）
// 判据：pipeline 规模翻倍时耗时应约翻倍（线性），而非约四倍（二次）。
// 该断言与机器绝对性能无关，只检验复杂度的量级。
const double t_n  = timePipeline(40000);
const double t_2n = timePipeline(80000);
const double ratio = t_2n / t_n;

// 实测：修复前 = 4.08（二次）；修复后 = 2.00（线性）。
// 阈值取 2.8，为 CI 噪声留出充足余量，同时仍能捕获二次退化。
assertLessThan(ratio, 2.8);
```

同时断言 B2 的分配放大：

```cpp
// 一条 N 参数命令，无论分成多少片到达，参数复制总次数都应为 O(N)。
const std::size_t copies = countArgCopies(/*nargs=*/32000, /*chunk=*/16 * 1024);
assertLessThan(copies, 32000 * 2);   // 修复前实测 999,140
```

这两个测试都**不需要网络**，可以在 macOS 上跑，因此能直接进入现有的 `ctest` 流程 —— 恰好绕开了 §4.1 所述的平台限制。

### 10.4 性能回归门槛

安全性改造即使吞吐提升有限也有价值，但不能造成无法解释的退化。建议在动手**之前**就固定门槛：

- 小命令吞吐（`-c 50 -P 1`）不下降超过 5%。
- pipeline 吞吐（`-c 50 -P 128`）**必须**有数量级改善（B1 的直接结果）。
- p99 延迟不恶化；混合与 pipeline 场景目标降低至少 20%。
- 同负载 RSS 不增长；慢客户端场景 RSS 必须从「无界」变为「有界」。
- sys CPU 与每请求 `epoll_ctl` 次数显著下降。
- 多 Reactor 必须在 1 / 2 / 4 Reactor 下表现出**可解释的**扩展曲线，否则不合入这份复杂度。
- io_uring 必须与**优化后**的 epoll 对比，不得拿未优化版本当基线。

### 10.5 需要长期暴露的观测指标

修复不是终点。以下指标应通过 `INFO` 类命令持续暴露，它们是下一轮「阶段二：发现异常」的输入：

`connections_accepted` / `connections_closed` / `rejected_max_clients` / `protocol_errors` / `epoll_mod_calls` / `read_calls` / `write_calls` / `budget_exhausted_reads` / `budget_exhausted_commands` / `input_watermark_pauses` / `output_watermark_pauses` / `accept_paused_events` / `event_loop_iterations` / `event_loop_max_stall_us` / `pending_input_bytes_peak` / `pending_output_bytes_peak`

## 11. 更远的两步：准入条件

### 11.1 多 Reactor（P3）

只有当阶段一到阶段六走完、且 Linux 基线呈现以下画像时才启动：

- 单个 epoll/I/O 线程接近饱和；
- `read`/`send`/`epoll` 与协议解析在 CPU 中占比显著；
- 唯一命令执行器**尚未**接近一个核心的上限；
- 增加连接数时网络线程是明确瓶颈；
- 资源上限与背压已能阻止队列无限增长。

与当前 `Database` 最匹配的第一版架构：

~~~text
                       bounded request queue
acceptor -> N I/O reactors --------------------> one command executor
               ^                                      |
               |                                      v
               +------ response queues + eventfd -----+

I/O reactor 拥有：fd、Connection、输入/输出缓冲、各自的 epoll 实例
command executor 拥有：CommandHandler 和唯一可变的 Database
~~~

关键约束：

- `Connection` 只能由所属 Reactor 操作和销毁。
- 跨线程消息使用 `connection id + generation`，**不传裸 `Connection` 指针**。
- 请求与响应队列必须有界；队列满时通过暂停 `EPOLLIN` 把背压传回客户端。
- 单一 executor 按请求队列出队顺序执行，从而定义跨连接全局顺序；每连接的响应顺序必须保持。
- Reactor 由 `eventfd` 被响应队列唤醒。
- 请求已入队后客户端断开、fd 复用、半关闭、服务退出都要有明确状态机。
- **跨线程请求不能引用随时可能 compact 的输入缓冲** —— 这正是 §6.1 刻意不把 `args` 改成 `string_view` 的原因之一。

这个模型**不会**突破单命令执行器的 CPU 上限。若要并行命令执行，需按 key 分片数据库，并重新定义多 key 命令、`KEYS`、`SAVE`、热点 key、事务和跨分片顺序 —— 那是存储架构升级，不应伪装成一次网络优化。

### 11.2 io_uring（P4，仅作实验后端）

现在不做的理由是清楚的：

- 已经存在收益确定得多的问题：B1 是 **704×** 的算法问题，B2 是 **31×** 的放大问题；
- 没有任何证据表明 syscall 是当前主要 CPU 消耗（§4.6 显示每请求仅 4 次连接相关 syscall，且其中 1 次是可以直接删掉的）；
- 项目还没有真实的 epoll benchmark 与集成回归；
- io_uring 会引入异步 buffer 生命周期、SQ/CQ 背压、取消与关闭竞态、fd 复用、内核与 liburing 兼容矩阵；
- 它**不能**消除同步 `SAVE`、`KEYS`、响应编码和单线程 `Database` 的成本。

准入条件（需全部满足）：

1. §6 的 P0/P1 已完成，epoll 基线稳定可复现。
2. 目标部署环境固定为支持所需特性的 Linux 内核。
3. `perf` / `strace` 证明网络 syscall 与 wakeup 持续占 CPU 的 25%–30% 以上。
4. 命令执行器仍有余量，瓶颈确实在 I/O backend。
5. 已有 backend-neutral 的 `EventLoop`/`Transport` 接口，以及完整的断连、取消、压力测试。
6. PoC 相比**优化后**的 epoll 至少带来 15%–20% 可重复的吞吐提升，或明确的 p99 改善，且 RSS、错误率、CPU 均不退化。

实验必须保留 epoll 作为默认与回退路径，并**逐项**启用 registered buffers、registered files、multishot accept/recv。一次叠加所有高级特性会让正确性问题和性能来源都无法定位。

## 12. 最终路线图

~~~text
现状：epoll + 有预算 + 有背压 + 写侧游标 + 读侧 O(N²) 头删 + 帧重解析 + EMFILE 活锁
  |
  |  P0：算法与可用性（收益已被实测证明，语义不变）
  v
B1 读侧游标(704×) + B2 帧扫描检查点(31×) + B3 acceptor 暂停/恢复
  |
  |  P1：常数因子与可运维性
  v
B4 accept4/mask 缓存/短读 + B5 协议上限 + B6 reserve/move + B7 日志 + B8 配置
  |
  |  ——— 此处必须重新 profile：真正的下一个瓶颈只能由数据决定 ———
  v
P2：event-loop stall 可观测 + KEYS→SCAN + 快照式持久化
  |
  v  仅当 Linux 数据证明单 I/O 线程饱和
P3：N 个 I/O Reactor + 单个有序命令执行器
  |
  v  仅当 syscall 仍然主导
P4：epoll / io_uring 可替换后端 + A/B 证据
~~~

这条路线保留了单线程数据库最宝贵的两项性质 —— **实现简单性**和**命令顺序语义**，同时优先解决已经能从源码和微基准中确认的问题。

完成 P0/P1 后必须重新测量。**只有到那时才能回答真正的下一个瓶颈是协议解析、命令执行、内存带宽、磁盘持久化，还是 epoll 本身。** 在此之前的任何架构级判断都是猜测。

## 附录 A：本轮基准的复现方式

基准代码不依赖 `epoll`，直接编译真实的 `src/net/Protocol.cpp`，因此可在 macOS 上复现：

```bash
c++ -std=c++17 -O2 -DNDEBUG -I include \
    bench.cpp src/net/Protocol.cpp -o bench && ./bench
```

各实验的构造要点：

| 实验 | 构造 | 对照 |
| --- | --- | --- |
| §4.2 | N 条 `PING` 连续 pipeline | 真实 `parse` + `erase(0,n)` **vs** 游标 + `string_view` 参数 |
| §4.3 | N 条 `GET` + 32 字节参数 | 两组**均**构造 `vector<string>`，仅消费策略不同 |
| §4.4 | 单条 N 参数帧，按 16 KiB 分片投喂 | 统计 `args.size()` 累计值 = 实际参数复制次数 |
| §4.5 | N 元素数组 / 4 KiB–1 MiB 响应 | 现状 `+=` **vs** reserve；copy-append **vs** move |

方法约定：每组重复 5–7 次取**中位数**；规模按 2 倍递增以便直接读出复杂度阶数；`-O2 -DNDEBUG` 与项目 Release 配置一致。

**边界重申**：这些数字标定的是**复杂度阶数与相对量级**，不是服务端吞吐成绩。绝对收益必须在 Linux 上用 §2.4 的 workload 复测。
