# Mini_Redis_cpp 网络性能分析与升级建议

> 分析日期：2026-08-25
> 分析对象：当前 main 分支，HEAD 为 7d833a1
> 结论类型：源码审查 + 本地网络组件测试 + 定向微基准；尚未进行 Linux 真实 epoll 端到端压测

## 1. 执行摘要

这个仓库的网络层可以升级，而且当前最值得做的不是把 epoll 替换成 io_uring，也不是立即把数据库改成多线程。

现有实现已经具备一套可工作的单线程、水平触发 epoll Reactor：监听 socket 和客户端 socket 都是非阻塞的，读取会持续到 EAGAIN，部分写会保留，只有存在待发送数据时才订阅 EPOLLOUT，pipeline、分片请求和 TCP 半关闭也有基础测试覆盖。作为教学型 Redis 子集，这个起点是合理的。

当前更可能先限制吞吐和尾延迟的是用户态热路径与调度策略，而不是 epoll 本身：

1. 读写缓冲区从字符串头部反复 erase，会搬移剩余数据；长 pipeline 和部分写会把成本放大到近似二次复杂度。
2. 一个连接可以持续读到 EAGAIN、执行完全部已缓冲命令、再持续写到 EAGAIN，没有每轮预算，容易让其他连接饥饿。
3. 输入和输出缓冲没有上限，也没有高低水位背压；慢读客户端和不完整超大请求可以持续占用内存。
4. 每个客户端事件结束后都会执行 EPOLL_CTL_MOD，即使关注事件没有变化。
5. 每次监听事件只 accept 一个连接，突发建连会带来额外唤醒和排队。
6. RESP 参数、命令结果和数组响应存在多次分配与复制；固定 1 KiB 读块也会放大大请求下的 read 调用数。
7. 命令执行、KEYS 和 SAVE 都与网络 I/O 同步运行在一个线程中。尤其 SAVE 会执行全量编码、文件写入和 fsync，期间所有连接都停止服务。

因此推荐路线是：

- P0：先建立 Linux 端到端基准和事件循环可观测性。
- P1：优化现有 LT epoll，包括游标式缓冲、背压、每连接预算、批量 accept、按需 EPOLL_CTL_MOD、连接日志治理和资源上限。
- P2：若性能画像证明单网络线程已饱和而命令执行仍有余量，再引入“多 I/O Reactor + 单命令执行器”。
- P3：只有在 syscall/wakeup 已成为主要 CPU 成本、部署环境固定为较新 Linux、且 epoll 优化完成后，才把 io_uring 作为可替换后端做 A/B 实验。

一句话判断：**保留 epoll，先升级实现质量；现在直接切 io_uring，复杂度会先于收益到来。**

## 2. 分析范围、方法与证据边界

### 2.1 已检查的关键路径

- src/main.cpp：进程入口、全局 Database 和 CommandHandler、信号处理。
- src/net/Server.cpp 与 Server.hpp：监听、accept、epoll 注册、事件分发和连接生命周期。
- src/net/Connection.cpp 与 Connection.hpp：非阻塞读写和连接缓冲。
- src/net/Protocol.cpp 与 Protocol.hpp：RESP 解析与响应编码。
- src/command/Command.cpp：同步命令分派，包括 KEYS 和 SAVE。
- src/core/Database.cpp：全局 key 空间、KEYS 遍历和 RDB 保存入口。
- src/persistence/Rdb.cpp：RDB 全量编码、同步写盘与 fsync。
- tests/NetworkIoTest.cpp、tests/MultiClientIoTest.cpp：已有网络正确性测试。

### 2.2 本轮实际验证

当前分析主机是 macOS arm64，服务端直接依赖 Linux sys/epoll.h，因此无法在本机启动真实 Server 进行 epoll 压测。仓库中的 build/bin/mini_redis_server 是 Linux x86-64 ELF 产物，也不能在当前主机执行。

本轮使用 Apple Clang、C++17 和 O2 手工编译并运行了两个不依赖 epoll 的网络测试：

- NetworkIoTest：通过；覆盖 pipeline、分片输入、半关闭、1 MiB 响应的部分写与续写。
- MultiClientIoTest：通过；覆盖两个连接的响应隔离、请求顺序和共享数据库可见性。

这些结果能确认 Connection 与协议层的基础语义，但不能证明真实 TCP、accept、epoll 关注集切换、高并发、慢客户端或尾延迟表现。

### 2.3 定向微基准

为了验证读缓冲头删的复杂度，本轮在临时目录构造连续 PING pipeline，重复执行现有的“解析一条请求，然后 string.erase(0, consumed)”流程。程序以 Apple Clang O2 构建，每组重复 5 次，取后续稳定运行的中位数：

| pipeline 命令数 | 中位耗时 |
| ---: | ---: |
| 1,000 | 74 us |
| 5,000 | 1,639 us |
| 10,000 | 6,650 us |
| 20,000 | 37,154 us |
| 40,000 | 158,969 us |

命令数从 10,000 增加到 40,000 时，耗时约增加 24 倍，明显偏离线性增长。这不是服务端吞吐成绩，也没有隔离解析、参数分配和 erase 的各自占比；它只用于验证当前 pipeline 热路径确实存在超线性退化。最终性能收益仍必须在 Linux 真实服务端上复测。

## 3. 当前网络架构

### 3.1 请求链路

~~~text
TCP client
    |
    v
listen socket -- EPOLLIN --> accept_client()
                                  |
                                  v
                      Connection + unordered_map
                                  |
client fd -- EPOLLIN/RDHUP ------> read() until EAGAIN
                                  |
                                  v
                            read_buffer_
                                  |
                                  v
                   RESP parse + copy argv strings
                                  |
                                  v
                    CommandHandler::execute()
                                  |
                                  v
                        single shared Database
                                  |
                                  v
                   encode response + append string
                                  |
                                  v
                            write_buffer_
                                  |
                                  v
                   send() until empty or EAGAIN
                                  |
                       pending output ? EPOLLOUT
~~~

Server::run 在 src/net/Server.cpp:141-211 中完成整个循环。一次客户端事件内，网络读取、RESP 解析、命令执行、数据库访问、响应编码和网络写入都在同一线程串行完成。

### 3.2 epoll 模式

代码没有设置 EPOLLET，因此当前是默认的水平触发模式。客户端初始关注 EPOLLIN 和 EPOLLRDHUP；存在待发送数据时再增加 EPOLLOUT。

这套选择本身没有问题：

- LT 更容易实现公平预算和背压。
- 当前读写函数已经正确处理 EINTR、EAGAIN 和部分写。
- EPOLLOUT 不是永久开启，避免了 socket 常态可写造成的忙循环。

不建议为了“看起来更高性能”直接加 EPOLLET。当前 accept 没有 drain 到 EAGAIN，而且如果以后增加每轮处理预算，ET 模式还需要本地 ready queue、显式重调度或 EPOLLONESHOT rearm，否则容易把未处理工作卡住。是否切 ET 应由真实 wakeup 数据决定。

### 3.3 当前已经做对的部分

- 监听 socket 和客户端 socket 都使用非阻塞模式。
- read 循环能够区分 EOF、EINTR、EAGAIN 和真实错误。
- send 使用 MSG_NOSIGNAL（平台支持时），能避免对端关闭导致 SIGPIPE 终止进程。
- 部分写后保留剩余响应，并在需要时订阅 EPOLLOUT。
- 对端关闭写方向后，服务端仍会把已经排队的响应发送完成。
- RESP parser 能区分完整请求、不完整请求和协议错误，也能连续处理 pipeline。

后续优化需要保留这些行为，尤其不能为了减少复制而破坏输入分片、响应顺序、半关闭和部分写语义。

## 5. 详细分析

### 5.1 无界缓冲与缺失的端到端背压

Connection::readFromSocket 会把所有可读内容追加到 read_buffer_。如果请求不完整，process_client_input 直接返回并永久保留这些字节。parser 对 argc 的上限接近 INT_MAX，对 bulk 长度也没有项目级最大值。

写侧同样没有上限：每条命令的结果直接追加到 write_buffer_。即使客户端长期不读取、write_buffer_ 已经很大，update_client_events 仍会继续订阅 EPOLLIN，因此服务端会继续接收请求、执行命令并制造更多响应。

典型故障模式：

- 客户端声明一个很大的 bulk 长度，然后缓慢发送或永不发送完，输入缓冲持续增长。
- 客户端发送深 pipeline 但不读取结果，输出缓冲持续增长。
- KEYS、SMEMBERS、LRANGE、ZRANGE 等一次产生大响应，临时响应字符串和连接输出缓冲同时占用内存。
- 多个慢客户端同时出现时，进程可能在进入内核 socket 背压之前先被用户态缓冲拖垮。

推荐引入三层限制：

1. 协议层：最大 argc、最大 bulk、最大完整请求帧。
2. 连接层：最大输入缓冲和最大待发送字节数。
3. 调度层：输出达到高水位时暂停该连接 EPOLLIN，同时暂停执行该连接已经缓存在用户态的后续命令；下降到低水位后再恢复。达到硬上限时记录原因并关闭连接。

高低水位必须形成迟滞区间，不能只用一个阈值，否则在边界附近会频繁 EPOLL_CTL_MOD。初始阈值应作为配置项通过业务数据量验证，而不是写死成“Redis 标准值”。一个适合本项目做实验的起点可以是：输出高水位 4–8 MiB、低水位为高水位的 1/4、硬上限 32–64 MiB、单请求上限 16 MiB；这些数字只是压测起点，不是最终结论。

### 5.2 公平性：单个连接可以耗尽整个事件循环时间片

当前一次事件处理包含三段无界循环：

1. read 一直到 EAGAIN。
2. 解析并执行 read_buffer_ 中的全部完整命令。
3. send 一直到缓冲为空或 EAGAIN。

这种 drain-to-EAGAIN 策略有利于降低 syscall 次数，但在单线程服务器里会牺牲公平性。一个持续写入的连接或超长 pipeline 可以让后面的 ready fd 长时间得不到处理。吞吐可能看起来不错，普通客户端的 p99/p99.9 却会显著恶化。

建议为每次调度增加可配置预算，例如：

- accept 数量预算；
- 读取字节预算；
- 执行命令数量或执行时间预算；
- 写出字节预算。

LT epoll 允许未读尽的 socket 在下一轮继续报告可读。不过，如果请求已经全部进入用户态 read_buffer_，只是命令预算耗尽，内核可能已经没有可读数据，此时仅依赖下一次 EPOLLIN 会让剩余命令卡住。因此还需要一个本地 ready queue：连接只要仍有完整待执行请求，就进入队列；队列非空时 event loop 不能无限期阻塞在 epoll_wait。

这项改造的核心目标不是让每条命令绝对平均，而是给其他连接一个有界的等待机会。

### 5.3 缓冲区头删与复制放大

当前读侧每完成一条命令就执行：

~~~text
read_buffer_.erase(0, bytes_consumed)
~~~

写侧每次 send 成功后执行：

~~~text
write_buffer_.erase(0, written)
~~~

std::string 从头部删除必须搬移后面的全部内容。对于 N 条小请求组成的大 pipeline，第一条删除移动接近全部剩余数据，第二条再次移动，以此类推，总搬移量会接近二次增长。部分写也会在大响应上制造同类问题。

推荐的第一版数据结构：

~~~text
read storage:  std::string + read_offset
write storage: deque<string> + front_offset + queued_bytes
~~~

读侧消费只推进 read_offset；当已消费前缀超过阈值且占总容量较大比例时，再做一次集中 compact。写侧按响应块排队，对队首只推进 front_offset；一个块发送完成后 pop_front。这样既避免每次 memmove，也自然支持输出字节计数与高低水位。

进一步优化可以让 parser 接受 string_view 或“buffer + offset”，参数先返回视图，只在写入数据库或跨线程传递时复制。需要特别注意：视图生命周期必须短于输入缓冲的 compact、扩容和连接销毁；如果进入多 Reactor 的跨线程队列，请求必须拥有自己的稳定存储，不能裸传指向 Connection 缓冲的 string_view。

响应侧可以按收益逐步演进：

- sendResponse 接受可移动字符串，空队列时直接转移所有权。
- encodeArray 预估容量并 reserve，减少重复扩容。
- 大数组响应使用分块队列，避免先构造一个巨大字符串再复制进连接缓冲。
- 只有 profile 证明有收益后再考虑 writev/sendmsg；不要一开始引入复杂的零拷贝生命周期管理。

### 5.4 accept 与 epoll 控制面开销

监听 fd 使用 LT epoll，因此每次只 accept 一个连接不会永久漏掉剩余连接，但会造成：

- backlog 中的连接需要多次 epoll_wait 才能取完；
- 突发连接的建立延迟增大；
- 固定 backlog=128 时更容易在应用取连接不及时的阶段溢出；
- 每个连接还需要一次额外 fcntl 设置非阻塞。

建议改为 accept4，并带 SOCK_NONBLOCK | SOCK_CLOEXEC，循环到 EAGAIN 或达到本轮 accept 预算。监听 socket 本身也可以在 socket 创建时原子设置 SOCK_NONBLOCK | SOCK_CLOEXEC，epoll_create1 则使用 EPOLL_CLOEXEC。

客户端事件尾部目前无条件调用 update_client_events，进而执行 EPOLL_CTL_MOD。普通小请求通常在同一轮已经写完，关注集仍是 EPOLLIN | EPOLLRDHUP，仍会白做一次 syscall。

应在 Connection 中缓存当前 interest mask，只有以下状态变化时才 MOD：

- 输出从空变为非空：增加 EPOLLOUT。
- 输出从非空变为空：移除 EPOLLOUT。
- 输出到达高水位：暂停 EPOLLIN。
- 输出下降到低水位：恢复 EPOLLIN。
- 对端半关闭：移除读关注。

MAX_EVENTS=128 只是每次 epoll_wait 的返回批量上限，不会让更多 ready fd 永久丢失，但在大量 fd 同时 ready 时会增加循环和 syscall 次数。建议变成配置项，并在 128、512、1024 等批量下实测，而不是仅凭经验扩大。

### 5.5 固定 1 KiB 读块和解析分配

Connection 每次只用 1 KiB 临时缓冲调用 read。对小命令问题不大，但大 value、深 pipeline 和高带宽连接会需要更多 syscall，也更容易触发 read_buffer_ 多次扩容。

建议先把读块做成常量或配置项，在 4 KiB、16 KiB、64 KiB 上对比。16 KiB 是合理的实验起点，但最终应由吞吐、cache miss 和连接内存共同决定。

协议路径还有几项用户态成本：

- 每次客户端输入处理都会创建 RespParser。
- 每条命令创建新的 vector<string>。
- 每个 bulk 参数通过 substr 复制。
- 命令名通过复制后转大写。
- encodeArray 对每个元素构造临时 bulk response 并反复拼接。
- 命令返回的字符串还要追加到 write_buffer_。

这些成本很可能在 epoll 之前进入 CPU 火焰图。建议先完成 buffer offset 和容量治理，再用 profile 判断是否值得引入 arena、small-vector、string_view 或分块响应。

### 5.6 同步命令是网络尾延迟的一部分

尽管 SAVE、KEYS、LRANGE 等逻辑不在 net 目录，它们直接运行在 epoll 线程，所以必须纳入网络性能分析。

SAVE 的调用链会：

1. 遍历当前数据库并构造完整 RDB 字节数组。
2. 写入临时文件。
3. 对文件执行 fsync。
4. rename 替换目标文件。
5. 对父目录执行 fsync。

这些步骤全部同步完成，期间服务端不 accept、不 read、也不 write。数据集越大或磁盘尾延迟越高，所有客户端的请求延迟越差。KEYS 会线性遍历 key 空间并构建完整数组响应，也会形成事件循环长任务。

不能简单地把 SAVE 丢到普通线程池：当前 Database 和内部对象是可变、无锁的，后台线程直接遍历会与命令写入发生数据竞争，也无法保证快照一致性。可选方案需要明确语义：

- 教学型、Linux 优先：实现类似 BGSAVE 的 fork + copy-on-write。
- 跨平台：在命令线程建立不可变快照或版本化视图，再交给后台线程编码写盘。
- 最小改造：保留同步 SAVE，但增加 event-loop stall 指标，并明确它不属于在线低延迟路径。

长范围命令可以增加结果数量限制、游标式命令或分块响应，但这属于命令语义升级，需要与 Redis 兼容目标一起决定。

### 5.7 socket 参数与系统边界

生产 socket 当前只设置 SO_REUSEADDR 和 O_NONBLOCK。建议按用途区分：

- TCP_NODELAY：对小请求/小响应的交互延迟通常有帮助，可以默认开启但必须在真实网络而非仅 loopback 上验证。
- SO_KEEPALIVE：主要用于发现长时间失联连接，不是吞吐优化；应提供超时配置。
- SO_REUSEPORT：当前单 acceptor 没有直接收益，仅在多 Reactor 各自监听时评估。
- SO_RCVBUF/SO_SNDBUF：Linux 有自动调优，不应未经数据盲目放大；用户态高低水位应先建立。
- listen backlog：改为配置项，并确认系统 net.core.somaxconn 和 tcp_max_syn_backlog 的实际上限。
- RLIMIT_NOFILE：启动时检查可用 fd 上限，并让 max clients 低于该值且留出文件、epoll 和持久化余量。

MAX_EVENTS、backlog、最大连接数、读写预算和水位都应来自一个 ServerConfig，而不是散落的编译期常量。

### 5.8 所有权与稳定性问题

下面几项不是主要吞吐热点，但在继续升级前应清理：

1. epoll ADD 失败时，connections_.erase 会析构 Connection 并关闭 fd，随后代码又显式 close 同一个 fd。当前单线程下通常只是得到 EBADF，但它暴露了 fd 所有权不清；进入并发模型后风险更高。
2. Server 内部有一个未使用的 Database db_，实际命令却通过全局 g_cmd_handler 操作全局 g_db。构造 Server 时 db_ 还会再次读取 RDB，造成启动阶段重复加载和双数据库歧义。
3. createListenSocket 是未使用的第二套监听实现，而且忽略多个系统调用返回值。
4. accept 后设置非阻塞失败会通过 handle_error 终止整个进程；单个客户端初始化失败不应拖垮服务。
5. 单连接处理缺少异常隔离，一些分配或命令异常可以越过 run，最终让 main 退出。
6. SIGINT/SIGTERM handler 中执行 iostream、RDB 保存和 exit，不满足异步信号安全要求；Linux 上可以用 signalfd 接入 epoll，或使用 self-pipe 让事件线程安全收尾。

推荐让 main 创建唯一的 Database 和 CommandHandler，并通过构造函数注入 Server。Server 不应隐藏另一份数据库，也不应在请求路径依赖 extern 全局变量。

## 6. 升级路线比较

| 路线 | 能解决什么 | 不能解决什么 | 复杂度与风险 | 当前建议 |
| --- | --- | --- | --- | --- |
| 优化现有 LT epoll | 缓冲搬移、背压、公平性、accept、冗余 syscall、连接风暴和内存稳定性 | 单核命令执行上限、同步 SAVE 本身 | 低到中；集中在 Server、Connection、Protocol | 立即做，P0/P1 |
| 改为 EPOLLET | 可能减少重复 readiness 通知 | 用户态复制、命令阻塞、单核上限 | 中；预算调度和漏事件更难保证 | 暂不切换，先测 wakeup |
| 多 I/O Reactor + 单命令执行器 | 并行 accept/read/部分解析/write，隔离慢连接；保留 Database 单线程所有权 | 命令执行吞吐仍受单核限制 | 高；跨线程队列、响应路由、关闭竞态 | P2，有基准门槛后做 |
| 多执行器 / 数据分片 | 命令执行可使用多核 | 多 key、KEYS、SAVE、全局顺序和未来事务语义 | 很高，已超出网络层升级 | 当前不建议 |
| io_uring backend | 网络 syscall 占主导时可能降低提交/完成和唤醒成本 | 用户态复制、长命令、单线程数据库 | 很高；异步 buffer 生命周期、取消、内核兼容 | P3 实验，不做当前主线 |

## 7. 推荐实施方案

### 阶段 0：先建立可重复基线

仓库当前没有 benchmark 目标、脚本、历史数据或回归阈值。两个网络测试使用 AF_UNIX socketpair，完全绕过真实 TCP、listen、accept 和 epoll。没有基线时直接换架构，很难判断收益来自哪里，也很难发现尾延迟和内存退化。

建议在 Linux 上固定 Release 构建：

~~~bash
cmake -S . -B build-perf -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=ON
cmake --build build-perf -j
ctest --test-dir build-perf --output-on-failure
./build-perf/bin/mini_redis_server
~~~

先用 redis-benchmark 建立可比基线。由于本项目只接受 RESP 数组，不支持 inline command，PING 应使用末尾自定义命令形式；不要直接使用内含 PING_INLINE 的默认测试组合：

~~~bash
# 单连接、无 pipeline：观察最小路径延迟和单连接吞吐
redis-benchmark -h 127.0.0.1 -p 6379 -n 100000 -c 1 -P 1 PING
redis-benchmark -h 127.0.0.1 -p 6379 -t set,get -n 100000 -c 1 -P 1

# 多连接、无 pipeline：观察调度和 epoll 行为
redis-benchmark -h 127.0.0.1 -p 6379 -n 1000000 -c 50 -P 1 PING
redis-benchmark -h 127.0.0.1 -p 6379 -t set,get -n 1000000 -c 50 -P 1

# 多连接、pipeline：放大解析、缓冲和响应发送热点
redis-benchmark -h 127.0.0.1 -p 6379 -n 1000000 -c 50 -P 16 PING
redis-benchmark -h 127.0.0.1 -p 6379 -t set,get -n 1000000 -c 50 -P 16
redis-benchmark -h 127.0.0.1 -p 6379 -n 1000000 -c 50 -P 128 PING
redis-benchmark -h 127.0.0.1 -p 6379 -t set,get -n 1000000 -c 50 -P 128

# 大 value：观察 read/send、分配和内存带宽
redis-benchmark -h 127.0.0.1 -p 6379 -t set,get -n 100000 -c 50 -P 16 -d 65536
~~~

还需要仓库内自带的场景驱动器或集成测试覆盖：

- 连接建立/断开风暴。
- 客户端只写不读，验证输出背压。
- 超大且永不完整的请求，验证输入上限。
- 一个深 pipeline 客户端与多个普通客户端混合，验证公平性。
- 大响应、部分写、半关闭和请求处理中断连。
- SAVE/KEYS 与普通 PING/GET 并发，量化 event-loop stall。
- 1 小时以上 soak，观察 RSS、fd 和连接状态是否稳定。

每轮至少记录：

- requests/s 或 commands/s。
- p50、p95、p99、p99.9 和 max latency。
- 单核利用率、总 CPU、user/sys 比例。
- 每请求 read、send、epoll_wait、epoll_ctl、accept 次数。
- RSS、连接数、每连接和全局 pending input/output 峰值。
- event loop 单轮耗时和最大 stall。
- 大 pipeline 干扰下普通客户端的 p99。

Linux 上可以结合 perf、strace -c、pidstat 和火焰图。采样工具本身会影响结果，因此“开采样定位”和“关闭采样出最终数字”应分开运行。

### 阶段 1：低风险优化现有 epoll

建议按以下顺序实施，每一步都保持测试通过并留下独立 benchmark 数据。

#### 1. 清理所有权和错误路径

- 删除未使用的 Server::db_ 和 createListenSocket。
- 通过构造函数注入唯一的 CommandHandler 或 Database。
- 修复 epoll ADD 失败时 double-close。
- 单连接 socket 初始化失败只关闭该连接。
- 使用 socket/accept4/epoll 的 CLOEXEC 标志。
- 给单连接处理增加异常边界。

这一步为后续并发和测试注入建立清晰边界。

#### 2. 改造读写缓冲

- read_buffer 改为 storage + read_offset。
- parser 接受有效区间，而不是要求每次从 string 的索引 0 开始。
- 达到阈值后集中 compact，禁止每条命令 erase 头部。
- write_buffer 改为响应块队列 + 队首 offset + queued bytes。
- sendResponse 支持 move，避免已有响应的额外复制。

先做算法级优化，再讨论 ring buffer、自定义 allocator 或 writev。

#### 3. 增加资源上限与背压

- 限制 argc、bulk、完整请求帧和连接输入缓冲。
- 维护输出 queued bytes。
- 高水位暂停 EPOLLIN，并停止处理该连接用户态输入中的后续命令；低水位时恢复。
- 硬上限关闭连接，并增加可观测的关闭原因。
- 增加 max clients；达到上限时明确拒绝新连接。

这里要测试一个命令本身产生超大响应的情况。仅在 enqueue 后检查硬上限太晚，因为巨大字符串已经分配完成；最终需要受限或分块的响应构建器。

#### 4. 增加公平调度预算

- 每轮限制 accept 数量、读字节、命令数和写字节。
- 增加本地 ready queue 处理已在用户缓冲中的完整命令。
- 达到预算时主动让出，让其他 ready fd 获得执行机会。
- 记录 budget exhausted 计数，确认配置是否过小或热点连接是否异常。

#### 5. 减少系统调用和连接风暴成本

- accept4 批量接收直到 EAGAIN 或达到预算。
- 缓存 epoll interest mask，仅在状态变化时 EPOLL_CTL_MOD。
- 避免已知不可写且只收到 EPOLLIN 时反复试探 send 并立刻得到 EAGAIN。
- 将连接日志改为等级控制、采样或异步聚合；热路径禁止每连接 std::endl flush。
- 把 backlog 和 event batch 大小变为配置项。

#### 6. 按 profile 减少解析和编码分配

- 读块大小从 1 KiB 做参数化 A/B。
- args 容量按 argc reserve。
- parser 评估 string_view，但严格管理生命周期。
- encodeArray 预估容量或分块编码。
- 命令分派若进入火焰图，再把长 else-if 链改为静态查找表。

完成阶段 1 后应重新 profile。如果 command executor 已经占满一个核心，后续重点应转向协议、命令和数据结构优化；只有 I/O 线程仍是主瓶颈时，才进入下面的多 Reactor 阶段。

### 阶段 2：有条件引入多 Reactor

只有阶段 1 完成后出现以下画像，才建议进入多 Reactor：

- 单个 epoll/I/O 线程接近饱和；
- sys CPU、read/send/epoll 或协议解析占比显著；
- 唯一命令执行器尚未接近一个核心的上限；
- 增加客户端连接数时网络线程成为明确瓶颈；
- 资源上限和背压已经能够阻止队列无限增长。

与当前 Database 最匹配的第一版架构是：

~~~text
                       bounded request queue
acceptor -> N I/O reactors --------------------> one command executor
               ^                                      |
               |                                      v
               +------ response queues + eventfd -----+

I/O reactor owns: fd, Connection, input/output buffer, epoll instance
command executor owns: CommandHandler and the only mutable Database
~~~

这个结构能并行化连接 I/O 和部分协议处理，同时保留数据库无锁、命令串行和单命令原子性。关键约束：

- Connection 只能由所属 Reactor 操作和销毁。
- 跨线程消息使用 connection id + generation，不能传裸 Connection 指针。
- 请求和响应队列必须有界；队列满时通过暂停 EPOLLIN 把背压传回客户端。
- 单一 executor 按请求队列出队顺序执行，从而定义跨连接全局顺序；每个连接的响应序号和发送顺序必须保持。
- Reactor 用 eventfd 被响应队列唤醒。
- 客户端在请求已入队后断开、fd 被复用、半关闭和服务退出都要有明确状态机。
- 跨线程请求不能引用随时可能 compact 的输入缓冲；需要拥有参数或引用计数的稳定数据块。

这个模型不会突破单命令执行器的 CPU 上限。如果 profile 已显示 CommandHandler/Database 占满一个核心，多 I/O Reactor 只会增加队列和上下文切换，收益有限。

要进一步并行命令执行，需要按 key 分片数据库，并重新定义多 key 命令、KEYS、SAVE、热点 key、未来事务和跨分片顺序。这已经是存储架构升级，不应伪装成一次网络优化。

### 阶段 3：将 io_uring 保持为可替换实验后端

当前不建议把 io_uring 设为主线，原因是：

- 已经存在收益更确定的 O(N²) 搬移、无背压和不公平问题。
- 没有证据表明 syscall 是当前主要 CPU 消耗。
- 项目还没有真实 epoll benchmark 与集成回归。
- io_uring 会引入异步 buffer 生命周期、CQ/SQ 背压、取消与关闭竞态、fd 复用、内核和 liburing 兼容矩阵。
- 它不能消除同步 SAVE、KEYS、响应编码和单线程 Database 的成本。

建议设置明确准入条件：

1. 阶段 1 已完成，epoll 基线稳定。
2. 目标部署环境固定为支持所需特性的 Linux 内核。
3. perf/strace 证明网络 syscall 与 wakeup 占 CPU 的显著比例，例如持续超过约 25%–30%。
4. 命令执行器仍有余量，瓶颈确实在 I/O backend。
5. 已有 backend-neutral 的 EventLoop/Transport 接口和完整的断连、取消、压力测试。
6. PoC 相比优化后的 epoll 至少带来约 15%–20% 可重复吞吐提升，或有明确 p99 改善，同时 RSS、错误率和 CPU 不退化。

io_uring 实验必须保留 epoll 默认和回退路径，并逐项启用 registered buffers、registered files、multishot accept/recv 等能力。不要一次叠加所有高级特性，否则正确性问题和性能来源都难以定位。

## 9. 验收标准

### 9.1 正确性与资源安全

- 现有 pipeline、分片输入、部分写、半关闭和多客户端测试继续通过。
- 增加真实 TCP/epoll 集成测试，响应内容和单连接顺序无变化。
- 任意不完整请求不能让单连接输入超过配置硬上限。
- 慢读客户端不能让单连接输出超过配置硬上限。
- 高低水位切换不会忙循环，也不会把已有完整请求永久卡住。
- 连接关闭、fd 复用、epoll ADD/MOD 失败路径没有 double-close 或 use-after-free。
- ASan/UBSan 通过；进入多 Reactor 后增加 TSan。

### 9.2 算法与调度

- pipeline 缓冲处理从反复头删改为近线性；对足够大的 N，T(2N)/T(N) 应接近线性范围，而不是持续向 4 倍靠近。
- 单次事件处理不超过配置的命令/字节预算。
- accept 队列能在一次或少量批次中排空，而不是每次事件只取一个。
- 关注集不变时不调用 EPOLL_CTL_MOD；记录 mod 次数验证下降幅度。
- 大 pipeline 客户端存在时，普通客户端 p99 有明确上界，不再随 pipeline 深度无界放大。

### 9.3 性能回归门槛

安全性改造即使吞吐提升有限也有价值，但不能造成不可解释的明显退化。建议在改动前固定门槛，例如：

- 小命令吞吐不下降超过 5%。
- p99 延迟不恶化，目标是在混合或 pipeline 场景降低至少 20%。
- 同负载 RSS 不增长，慢客户端场景 RSS 必须变为有界。
- sys CPU 和每请求 epoll_ctl 次数显著下降。
- multi-reactor 必须在 1、2、4 Reactor 下表现出可解释扩展，否则不合入复杂架构。
- io_uring 必须与优化后的 epoll 比较，不能拿未优化旧版本做基线。

绝对目标应根据实际硬件和业务负载确定；这里更强调可重复、同环境、同版本工具下的相对变化。

## 10. 建议的提交拆分

为了让性能收益和正确性风险可审查，建议拆成以下独立变更：

1. benchmark 与指标：真实 Linux 集成测试、固定 workload、event-loop stall 和缓冲指标。
2. 所有权与稳定性：依赖注入、double-close、accept4/CLOEXEC、异常隔离、日志开关。
3. 缓冲算法：read offset、write chunk queue、集中 compact，保持协议语义不变。
4. 背压与资源限制：协议上限、连接水位、max clients。
5. 公平调度：读/命令/写预算和本地 ready queue。
6. epoll 控制面：批量 accept、按需 MOD、批量大小配置、TCP_NODELAY A/B。
7. profile 驱动的解析/编码优化。
8. 达到准入条件后，单独设计 multi-reactor；io_uring 再作为独立实验分支。

## 11. 最终建议

短期内，最有性价比的升级不是更换 epoll，而是把现有 Reactor 从“能工作”提升为“有界、可观测、公平、低搬移”：

~~~text
当前：epoll + drain everything + unbounded strings + synchronous commands
  |
  v
P1：epoll + budgets + backpressure + cursor/chunk buffers + batched accept
  |
  v  only if profiling proves the need
P2：N I/O reactors + one ordered command executor
  |
  v  only if syscall remains dominant
P3：epoll/io_uring replaceable backends with A/B evidence
~~~

这条路线保留了当前单线程数据库最重要的简单性和命令顺序语义，同时先解决已经能从代码和微基准确认的问题。完成阶段 1 后再测一次，届时才能回答真正的下一瓶颈是协议解析、命令执行、内存带宽、磁盘持久化，还是 epoll/syscall。
