# Mini_Redis_cpp 读写并发、写时复制与锁设计

> 设计日期：2026-08-25
> 基线版本：`564e8f8`
> 文档状态：设计提案，本文描述的 COW、后台快照和并发锁尚未在当前代码中实现。

## 1. 执行摘要

当前项目并没有数据库锁：所有网络事件和命令都在同一个 `epoll` 线程中串行执行。正常请求路径目前不会发生线程间数据竞争；它的主要问题是 `SAVE`、`KEYS`、大范围读取和深 pipeline 会阻塞整个事件循环。此时直接给每个数据库接口加锁，不能增加并行度，只会增加开销和复杂度。

本设计建议把演进拆成两个相互兼容的目标：

1. **近期目标：单数据库执行线程 + 对象级写时复制（COW）快照。** 数据库仍由一个线程修改；创建 RDB 快照时只复制 key 和对象句柄，后台线程只读不可变旧版本。前台第一次修改被快照共享的 key 时，才深拷贝该对象。这个阶段不需要数据库读写锁。
2. **远期目标：确有并行执行命令的性能证据后，引入固定分片锁。** key 空间拆成固定数量的 shard；先用普通互斥锁验证正确性，只有并发读收益明确时，才切换为有显式排队规则的读写锁。短读在共享锁内完成，长读通过 COW 句柄固定版本后在锁外完成，写操作在对应 shard 的排他锁下 detach 和修改。

推荐的最终组合不是“到处加锁”，而是：

```text
固定 shard 负责：key 目录、发布新版本、命令原子性
COW 版本负责：对象生命周期、锁外长读、后台一致性快照
统一锁顺序负责：多 key 命令无死锁
queue-fair 策略负责：限制已登记读者和写者之间的插队，以无算法性饥饿为目标
```

自定义智能指针应放在 `Database` 的 value 层：

```cpp
std::unordered_map<std::string, CowPtr<RedisObject>> data_;
```

不应把 COW 下沉到 `HashEntry`、List 元素或 ZSet 的两个索引中。一个 Redis key 是当前命令和快照天然的一致性单元；按 key 复制最容易保持对象内部不变量，也最贴合现有接口。

## 2. 目标与非目标

### 2.1 目标

- 后台 RDB 编码和文件 I/O 不长期阻塞前台写命令。
- 快照代表一个明确时刻的完整数据库状态，不出现“部分旧、部分新”的模糊视图。
- 读者只能看到某个完整版本，不能观察到容器迁移或复合更新的中间状态。
- 首次修改共享对象时才复制；未修改对象继续由活动数据库和快照共享。
- 并行执行命令后，不同 shard 可以并行，同一个 key 的写入仍保持串行和原子。
- 明确定义锁顺序、公平性、生命周期和内存上限，避免死锁、读/写饥饿和快照内存失控。
- 保留当前 Redis 风格的“单条命令原子执行”语义。

### 2.2 非目标

- 本文的 COW 指 C++ 进程内、按 Redis key 对象复制的用户态 COW，不是 `fork()` 依赖操作系统页表的进程级 COW。
- 本阶段不实现无锁哈希表、hazard pointer、epoch reclamation 或通用 MVCC 数据库。
- 不承诺同一热点 key 的写操作可以并行；这会破坏对象级原子性。
- 不在首版实现容器页级 COW 或持久化树。大对象首次写入的 O(N) 复制先通过指标评估。
- 不用锁解决网络层公平调度。单连接读到 `EAGAIN`、执行完全部 pipeline 的问题仍应由事件预算和 ready queue 解决。
- 不改变现有 Redis 命令返回语义和 RDB 文件格式。

## 3. 当前实现与问题边界

### 3.1 当前请求路径是串行的

当前服务端只有一个事件循环：

```text
epoll_wait
   -> 读取某个 Connection
   -> 解析其所有完整请求
   -> CommandHandler::execute
   -> Database / RedisObject 原地读写
   -> 写回响应
```

证据包括：

- `Server::run()` 逐个处理 ready fd，见 `src/net/Server.cpp:141`。
- `process_client_input()` 同步调用全局 `CommandHandler`，见 `src/net/Server.cpp:117`。
- `CommandHandler` 只保存一个 `Database&`，见 `include/mini_redis/command/Command.hpp:9`。
- CMake 虽链接线程库，但注释也明确当前为单线程，见 `CMakeLists.txt:19`。

因此，当前正常命令路径没有“锁饥饿”；已有的是**调度饥饿**：深 pipeline、大范围查询或同步 `SAVE` 可长期占用事件线程。锁不能替代每轮读字节、命令数和写字节预算。

### 3.2 `shared_ptr` 不是 COW

`Database` 当前保存：

```cpp
std::unordered_map<std::string, std::shared_ptr<RedisObject>> data_;
```

见 `include/mini_redis/core/Database.hpp:75`。`HSET`、List、Set 和 ZSet 写命令取得同一个对象后直接原地修改。复制 `Database` 或复制这张 map 只会共享可变对象；一个副本的写入会污染另一个副本。

`shared_ptr` 只保证不同智能指针实例对控制块引用计数的并发操作安全，不保证：

- `unordered_map` 可以并发读写；
- `RedisObject` 内部容器可以并发读写；
- 仅凭 `use_count() == 1` 就能在没有外部同步的情况下安全写入。

### 3.3 直接后台 `SAVE` 会产生数据竞争

`Database::saveRdb()` 当前把 `data_` 的引用直接交给 RDB 编码器，见 `src/core/Database.cpp:401`；编码器遍历整个 map 和对象，见 `src/persistence/Rdb.cpp:917`。如果简单地把这段逻辑移到后台线程，前台写入会同时修改 map 或对象内部容器，可能导致：

- `unordered_map` 迭代器失效；
- List/Set/Hash 编码切换时读取到破坏的 `variant` 状态；
- Hash 渐进式 rehash 时遗漏或重复字段；
- ZSet 的 `score_map_` 和 `sorted_set_` 被读到不一致的中间状态；
- use-after-free、崩溃或生成无法加载的 RDB。

### 3.4 当前最现实的并发缺陷是信号重入

`src/main.cpp:15` 的信号处理函数直接使用 iostream、调用 `saveRdb()` 并 `exit()`。信号可在任意对象写到一半时打断主线程，这些操作也都不是 async-signal-safe。即使保持单线程，也应优先改为 `signalfd` 或 self-pipe/eventfd：信号处理器只发通知，由事件循环在安全点完成退出和保存。

### 3.5 COW 落地前的代码障碍

- `RedisObject` 没有多态 `clone()`。
- `Dict` 的 bucket 链由 `unique_ptr<HashEntry>` 管理，并明确禁用复制，见 `include/mini_redis/core/Dict.hpp:23`。
- `lookupKey()` 从 const 方法返回可变的 `shared_ptr<RedisObject>`，只读约束没有被类型系统封住。
- `get_rehashing_dicts()` 返回内部裸 `Dict*`；对象被覆盖或删除后可能悬空，也能绕过 COW 直接修改旧版本。
- `Server` 内有一份未使用的 `Database db_`，真正的命令却操作 `main.cpp` 中的全局 `g_db`。引入快照前必须收敛为唯一活动数据库。

## 4. 必须长期成立的并发不变量

实现时应把以下规则视为接口契约，而不是编码习惯：

1. **活动目录受所有者或 shard 锁保护。** map 中 `CowPtr` 实例的读取、替换和删除不能无同步并发。
2. **已发布的共享版本不可变。** 只要一个对象被快照或锁外读句柄共享，任何写入都必须先 detach。
3. **可变访问不能逃逸。** `CowPtr` 不提供公开的可变 `operator->()`、`get()` 或隐式 `T*` 转换。
4. **引用计数不等于数据锁。** 原子引用计数只管理生命周期；payload 的发布和写入仍由数据库所有权或 shard 排他锁保证。
5. **一个对象是一个一致性单元。** Hash 的编码和 rehash 状态、ZSet 的两份索引必须一起复制、一起发布。
6. **维护操作也是写。** rehash、编码升级、缓存更新只要会改内存，就必须走相同的 detach/排他锁路径。
7. **多锁只按 shard id 升序获取、逆序释放。** 禁止按客户端参数顺序加锁。
8. **不做锁升级。** 写命令一开始就申请排他锁，不能先持共享锁再等待排他锁。
9. **数据库锁内禁止不可控阻塞。** 文件 I/O、`fsync`、socket I/O、日志 flush、等待线程和用户回调均不得在 shard 锁内执行。
10. **快照有唯一一致性点。** 完整快照必须在所有相关 shard 同时被读锁保护时取得；逐 shard 复制并立即释放只能得到模糊快照。

## 5. 方案比较与决策

| 方案 | 优点 | 主要问题 | 结论 |
| --- | --- | --- | --- |
| 单线程所有权 | 无数据库锁、顺序语义清楚 | 单个执行核上限，长命令阻塞 | 当前和近期默认 |
| 一把全局 `mutex` | 没有 reader/writer 两类准入策略，正确性更容易验证 | 所有命令串行；标准不保证 FIFO 或线程无饥饿 | 并发改造的短期正确性脚手架 |
| 一把全局 `shared_mutex` | 多读者可并行 | C++17 不保证公平；长读/SAVE 阻塞所有写 | 不作为最终方案 |
| map 锁 + 每对象锁 | 不同 key 并行度高 | 两层锁顺序、对象生命周期、多 key 死锁复杂 | 首版不采用 |
| 每 key 动态锁表 | 粒度最细 | 锁条目回收、热点、哈希攻击和内存开销复杂 | 暂不采用 |
| 固定 shard + 队列公平读写锁 | 生命周期与对象由同一锁保护；可控、易排序 | 同 shard 不同 key 会伪冲突；自定义锁需严格验证 | 并行命令经验证后的目标方案 |
| 全量深拷贝快照 | 语义简单 | 创建快照暂停和内存均为 O(数据集) | 仅作测试基线 |
| key 级 COW 快照 | 创建只复制目录；只复制被修改对象 | 大对象首次写延迟和额外内存 | 推荐快照方案 |
| lock-free/RCU/MVCC | 潜在高读吞吐 | 回收、ABA、多 key 一致性和调试成本高 | 当前不值得 |

“最优锁”取决于执行模型和负载。对当前仓库，最优解是继续维持数据库单线程所有权；只有命令执行本身经 profile 证明成为瓶颈时，才启用 shard 锁。对并行版本，建议从 64 个固定 shard 起步，再用 16/64/256 的基准结果调整，不在运行时改变 shard 数。

## 6. 目标架构

### 6.1 近期：单写者 COW 快照

```text
                   唯一数据库执行线程
                  /         |          \
             普通读      前台写      创建 Snapshot
                           |              |
                     CowPtr::detach       | 有界队列
                                          v
                                    RDB 后台线程
                                 仅 const 读取旧版本
                                 编码、write、fsync
```

数据库线程创建快照时没有并发 map 写者，因此无需数据库锁。快照发布给后台线程后，活动数据库仍是唯一写者；它对被快照共享的对象执行首次写入时 detach。

### 6.2 远期：并行命令 + shard 锁 + COW

```text
             N 个命令工作线程
                     |
          shard_for(key) / 排序去重
                     |
     +---------------+---------------+
     |               |               |
  Shard 0          Shard 1        Shard 63
 queue-fair RW     queue-fair RW   queue-fair RW
 map<key,CowPtr>   map<key,CowPtr> map<key,CowPtr>
     |               |               |
     +------ 不可变版本 / COW --------+
                     |
        DatabaseSnapshot -> RDB worker
```

建议的数据布局：

```cpp
class Database {
    static constexpr std::size_t kShardCount = 64;

    struct alignas(64) Shard {
        QueueFairRwLock mutex;
        std::unordered_map<std::string, CowPtr<RedisObject>> values;
        std::uint64_t version = 0;
    };

    std::array<Shard, kShardCount> shards_;
};
```

`alignas(64)` 只是减少相邻热点锁的伪共享，最终仍应以目标平台 cache line 和基准为准。shard 数使用 2 的幂，可以通过 `hash(key) & (N - 1)` 定位。

## 7. 自定义 `CowPtr` 设计

### 7.1 API 必须让误用变困难

推荐接口只公开 const 访问，把 detach 限制给 `Database` 或受控的写访问器：

```cpp
template <class T>
class CowPtr {
public:
    CowPtr() noexcept = default;
    CowPtr(const CowPtr& other) noexcept;
    CowPtr(CowPtr&& other) noexcept;
    CowPtr& operator=(const CowPtr& other) noexcept;
    CowPtr& operator=(CowPtr&& other) noexcept;
    ~CowPtr();

    const T* get() const noexcept;
    const T& operator*() const noexcept;
    const T* operator->() const noexcept;
    explicit operator bool() const noexcept;

private:
    T& detach();                 // 可能深复制；只允许 Database 调用
    bool unique() const noexcept;
    friend class Database;
};
```

刻意不提供以下接口：

- `T* get()`；
- 非 const `operator->()`；
- “写时自动 detach”的隐式代理；
- 从裸指针随意构造多个控制块。

隐式写代理很容易与当前按值返回的 `lookupKey()` 组合出错误：局部 `CowPtr` detach 后只修改局部副本，map 中仍指向旧对象，修改在函数返回时丢失。写访问必须定位并修改 map 内的那个句柄。

### 7.2 多态复制协议

`RedisObject` 增加：

```cpp
class RedisObject {
public:
    virtual ~RedisObject() = default;
    virtual std::unique_ptr<RedisObject> clone() const = 0;
    // type() / memory_usage() 保持不变
};
```

各对象的复制要求：

| 对象 | clone 策略 | 注意点 |
| --- | --- | --- |
| String | 复制 `std::string` | `SET` 通常直接替换，无需先 clone |
| List | 复制整个 `variant<vector, deque>` | 保持当前编码 |
| Set | 复制 `intset` 或 `unordered_set` | 保持 INTSET/STRSET 编码 |
| ZSet | 同时复制 hash index 和 ordered set | 两份索引必须来自同一受保护版本 |
| Hash | 复制 ziplist 或深复制 `Dict` | 必须支持正在 rehash 的状态 |

`Dict` 深复制不能简单调用 `get_all()` 后重建，因为那会丢失 `ht_[0]`、`ht_[1]`、bucket 数和 `rehashidx_`，也可能改变下一次操作的成本。应逐 bucket 深复制链表节点，并保留双表尺寸、`used_` 和 rehash 进度。

### 7.3 控制块与引用计数

若实现完整的自定义引用计数，控制块至少包含：

```cpp
struct ControlBlock {
    std::atomic<std::size_t> strong{1};
    RedisObject* object;
};
```

约束如下：

- 拷贝句柄用 `memory_order_relaxed` 的 CAS 循环增加强引用，并在同一个原子步骤中检查上限；由于复制构造为 `noexcept`，计数到达上限时采取 fail-fast（例如 `std::terminate`），不能让 `fetch_add` 回绕。
- 释放使用经典的 release + acquire fence 模式；最后一个引用负责销毁对象和控制块：

  ```cpp
  if (strong.fetch_sub(1, std::memory_order_release) == 1) {
      std::atomic_thread_fence(std::memory_order_acquire);
      delete object;
      delete control_block;
  }
  ```

  也可以用 `fetch_sub(1, std::memory_order_acq_rel)` 实现更保守的等价释放路径，但应以基准确认成本。
- clone 和新控制块必须全部构造成功后，才能替换当前句柄并释放旧引用，保证 detach 本身的强异常安全。
- 控制块引用计数允许不同 `CowPtr` 实例跨线程销毁；它不允许同一个 `CowPtr` 实例被无锁并发读写。map 中的实例仍由所有者或 shard 锁保护。
- 对象发布到后台队列还需要队列自身的 happens-before；引用计数不是对象发布屏障。
- 实现必须在增加引用前防止计数溢出；Debug 断言只作为额外诊断，Release 构建不能允许计数回绕。空指针、移动后状态和自赋值必须有单元测试。

工程上更稳妥的第一步，是先实现一个**自定义语义包装器**，内部暂用 `std::shared_ptr<T>` 管理控制块，但只暴露上述 const API 和私有 `detach()`。这样先验证 COW 边界；若项目的学习目标包含引用计数实现，再在不改变上层 API 的情况下替换内部控制块。两种实现都不能绕过数据库同步契约。

### 7.4 `unique()` 快路径何时才安全

以下条件必须同时成立，才能在 `strong == 1` 时原地写：

1. 当前线程持有该 key 所属 shard 的排他锁，或它就是唯一数据库线程；
2. 所有快照和锁外读者都持有独立 `CowPtr`，不会使用裸指针延长生命周期；
3. 新的读句柄只能在相同 shard 锁下从 map 复制，因而不会在检查 `unique()` 后突然出现；
4. 对象没有其他可变别名。

所以 `unique()` 是受锁协议保护的复制优化，不是并发正确性的判据。

## 8. 数据库读写 API 设计

### 8.1 区分短读与固定版本长读

提供两类内部 API：

```cpp
// 在 shared lock 内调用只读回调，适合 GET/HGET/LLEN 等短操作。
template <class F>
auto withRead(const std::string& key, F&& fn) const;

// 在 shared lock 内复制 CowPtr，随后锁外只读，适合范围查询和后台任务。
ReadHandle pinRead(const std::string& key) const;
```

两者权衡：

- 短读不产生长寿命共享版本，写者通常可以原地修改。
- `pinRead()` 很快释放锁，但句柄存活期间的第一次写会复制整个对象。
- `LRANGE`、`SMEMBERS`、`ZRANGE` 等 O(N) 读取可按对象规模阈值选择锁内读或 pin 后锁外读；阈值必须由基准决定。
- 返回对象内部字符串引用的接口不能越过 guard/handle 生命周期；对外优先返回值。

### 8.2 写访问必须作用于 map 内句柄

写路径不再使用“按值 lookup + mutable cast”，而由数据库集中完成：

```cpp
template <class Object, class Create, class Mutate>
auto mutateKey(const std::string& key, Create&& create, Mutate&& mutate);
```

逻辑顺序是：

1. 直接取得目标 shard 的排他锁。
2. 在 map 内查找或创建对象。
3. 校验类型。
4. 对 map 内的 `CowPtr` 调用一次 `detach()`。
5. 在同一临界区内完成该命令对对象的全部修改。
6. 必要时删除空对象，增加 shard version。
7. 释放锁后构造 RESP 或执行其他慢操作。

`HSET`、`SADD`、`ZADD`、`LPUSH` 和 `RPUSH` 一条命令包含多个元素时，只能 detach 一次，不能每个 field/member 都检查和复制一次。

`withRead()` 和 `mutateKey()` 的回调是 Database 私有、同步且非重入的内部函数：不得再次调用任何会获取 shard 锁的 Database API，不得等待任务，也不得调用网络、日志或用户扩展代码。跨 key 操作必须先通过统一的 multi-shard guard 取得完整锁集，再调用明确标记为 `...Locked` 的 private helper。

### 8.3 替换与删除不需要深拷贝

- `SET` 直接构造新 `StringObject` 并替换活动 entry；旧快照继续持有旧对象。
- `DEL` 只从活动 map 删除句柄；对象是否销毁由所有快照和读句柄的引用计数决定。
- 类型覆盖也发布新句柄，不修改旧对象。

### 8.4 内部维护操作

应删除 `get_rehashing_dicts()` 返回裸指针的接口，改为：

```cpp
std::size_t Database::advanceRehash(std::chrono::microseconds budget);
```

它在数据库内部选择 key、取得相应 shard 排他锁、必要时 detach，再推进有限步数。不能让后台线程保存一个锁外 `Dict*`。即使 rehash 不改变逻辑键值，它也会移动节点，因此在并发与 COW 语义上属于写操作。

## 9. 快照与后台 RDB

### 9.1 快照表示

RDB 编码只需顺序遍历，快照不必复制成另一张哈希表：

```cpp
struct SnapshotEntry {
    std::string key;
    CowPtr<RedisObject> value; // 只能 const 访问
};

class DatabaseSnapshot {
    std::uint64_t sequence;
    std::vector<SnapshotEntry> entries;
};
```

快照创建成本是 O(key 数量 + key 字节数)，而不是 O(全部 value 字节数)。对象内容只增加引用计数。

### 9.2 一致性时刻

单数据库线程模式下，在两条命令之间复制目录即可。并行命令模式下：

1. 按 shard id 升序取得所有 shard 的共享锁。
2. 统计 entry 数并为 vector 预留空间。
3. 复制每个 key 和 `CowPtr`。
4. 目录复制成功后、仍持有全部 shard 锁时，通过数据库级原子单调计数器 `fetch_add` 分配 snapshot sequence；共享 shard 锁本身不能串行化两个快照创建者。
5. 逆序释放所有 shard 锁。

最后一个 shard 共享锁取得后，到任意 shard 锁释放前，整个数据库都保持稳定。目录复制成功后的 sequence 分配操作就是快照的精确线性化点；快照内容在该点与活动数据库相同，sequence 表示这个线性化顺序，而不是 worker 开始或完成的顺序。如果目录复制抛出异常，则不分配 sequence，也不发布快照。不能锁一个 shard、复制后立即释放，再处理下一个 shard，否则并发多 key 写入会让 RDB 不对应任何真实时刻。

目录复制期间会短暂阻塞写者，但对象编码、CRC、临时文件写入、文件 `fsync`、原子 `rename` 和目录 `fsync` 全部在锁外执行。相比当前同步 `SAVE`，锁持有时间从 O(全部 value + 磁盘延迟) 降为 O(key 目录)。

### 9.3 保存任务策略

- 首版同一时刻最多允许一个 RDB 保存任务；新的 `BGSAVE` 直接返回 busy，不排队也不合并请求。这样任务状态、sequence 和内存上限都有唯一语义。只有未来明确设计 pending 合并协议后才能改变该行为。
- `SAVE` 可保留同步命令语义，但也应先取得不可变快照，再在数据库锁外编码。它仍会占用调用它的命令线程；真正消除事件循环停顿需要后台 worker。
- 快照通过有界任务队列发布，发布成功后后台线程只得到 const 视图。
- 保存失败沿用当前临时文件 + 原子替换规则，旧 RDB 不受影响。
- 为每个目标文件维护 `latest_accepted_sequence` 和独立的提交互斥。任务可以在锁外编码临时文件，但在最终 `rename` 前必须在提交互斥下确认自己的 sequence 仍是该目标允许提交的最新版本；较旧任务只删除自己的临时文件，不能覆盖新文件。取消或编码失败不回退单调计数器；不同目标文件可共享数据库快照序列，但提交状态按规范化后的目标路径隔离。首版只允许一个活动保存任务时，这套规则仍作为未来放开并发的明确契约。

### 9.4 COW 写放大与内存保护

快照存活期间：

- 未修改 key：不复制 value。
- `SET`/`DEL`：不复制旧 value，只保留快照引用。
- 首次修改 List/Set/Hash/ZSet：复制整个对象；活动版本随后通常恢复唯一，后续写可原地进行。
- 新快照建立后，该版本上的下一次写可能再次复制。

最坏情况下，快照期间几乎所有大对象都被修改，额外内存接近完整数据集；ZSet 还要复制两份索引。必须记录：

- `snapshot.entries`、创建耗时和存活时间；
- `cow.detach.count`、按对象类型的复制字节和复制耗时；
- `cow.shared_bytes`、活动 RSS/PSS、保存队列长度；
- 因内存阈值拒绝或取消的保存次数。

建议配置 `max_snapshot_count = 1` 和 COW 额外内存软/硬阈值。首版采用“尽量保住写入、超限时先取消快照”的固定语义：数据库写线程在 detach 前根据对象 `memory_usage()` 做保守的 admission check，并以原子预算先预留估算的 retained bytes。预算 charge 与旧共享版本绑定，直到该旧控制块不再因快照/锁外读句柄而存活时才归还；clone 构造失败则立即归还。若预留失败，本次 mutate 尝试必须先退出并释放 shard 锁，再通过 cancellation token 取消后台快照；线程只能在锁外等待或确认 worker 不再读取，释放快照后重新从查找和类型检查开始执行该命令。如果仍有不可取消的读句柄占用预算或重试仍无法预留，则当前写命令失败。已经成功发布的写入不回滚。worker 在编码循环和进入文件提交区前检查取消状态；取消任务删除自己的临时文件。clone 抛出 `std::bad_alloc` 时，当前写命令失败且旧活动版本保持不变。

这里的统计是尽力保护，不是绝对 OOM 保证：对象估算可能低于 allocator 元数据、bucket 扩容、临时构造和 RSS 的真实峰值，而且 clone 必须先获得足够内存才能生成新版本。部署时仍需给进程预留内存余量，并通过真实负载校准估算系数。大对象在最后一个引用释放时析构也可能造成尾延迟；只有 profile 证明确有问题时，再引入后台延迟回收队列。

## 10. 锁粒度设计

### 10.1 为什么选择固定 shard

一把全局锁便于先验证正确性，但无法让无关 key 并行。给每个对象加锁又会引入“map 锁保护生命周期、对象锁保护内容”的两层锁图。固定 shard 让一把锁同时保护：

- shard 内 map 的查找、插入、删除和 rehash；
- map entry 中 `CowPtr` 的复制和替换；
- 当前活动对象的可变内容；
- 对象从非共享到共享、从共享到 detach 后新版本的转换。

这样没有 map 锁与对象锁之间的 ABBA 问题。代价是哈希到同一 shard 的不同 key 会伪冲突；64 个 shard 对当前教学型项目是合理起点。热点 key 自身仍必然串行，增加 shard 数不能解决单热点写竞争。

### 10.2 命令与锁模式

| 操作 | 锁模式 | 锁内工作 | 锁外工作 |
| --- | --- | --- | --- |
| `PING` | 无 | 无 | 参数处理和响应 |
| `GET/HGET/LLEN/SCARD/ZSCORE` | 单 shard 共享锁 | 查找、类型检查、复制小结果 | RESP 编码 |
| `LINDEX/LRANGE/SMEMBERS/ZRANGE` | 共享锁或 pin | 小对象可锁内复制；大对象固定 const 版本 | 长遍历、结果编码 |
| `SET` | 单 shard 排他锁 | 构造完成后替换 entry | RESP 编码 |
| 复合对象写命令 | 单 shard 排他锁 | detach 一次、完整修改、必要时删除 | RESP 编码 |
| `DEL/EXISTS` 多 key | 多 shard 排他/共享锁 | 对 shard id 排序去重后完成整条命令 | RESP 编码 |
| `KEYS` | 所有 shard 共享锁 | 复制一致的 key 列表 | 排序/匹配/RESP 编码 |
| `SAVE/BGSAVE` | 所有 shard 共享锁 | 复制一致快照目录 | 编码和全部文件 I/O |
| `memory_usage` | 快照或所有 shard 共享锁 | 固定要统计的版本 | 深度统计 |
| 渐进 rehash | 单 shard 排他锁 | detach 后迁移有限 bucket | 无 |

数据库方法自己管理锁，调用者不能直接取得内部对象再决定加锁，以免漏锁。

### 10.3 多 key 锁顺序

所有多 key 命令执行同一流程：

```text
keys
  -> 计算 shard id
  -> shard id 排序并去重
  -> 按升序加锁
  -> 执行完整命令
  -> 按逆序释放
```

这避免了 `DEL a b` 与 `DEL b a` 的 shard 锁 ABBA 死锁。应提供统一 `MultiShardReadGuard` / `MultiShardWriteGuard`，禁止各命令重复手写排序逻辑。访问相交 key/shard 的命令受这些锁约束；访问完全不相交 shard 的命令可以并行，其间不承诺唯一的物理执行顺序。

当未来出现同时读部分 key、写部分 key 的命令时，先确定每个 shard 的最强模式：同一 shard 只获取一次锁，只要其中任意 key 要写，该 shard 就取排他锁。

## 11. 公平性策略与读写饥饿风险

### 11.1 不直接依赖 `std::shared_mutex` 的公平性

C++17 没有规定 `std::shared_mutex` 是读优先、写优先还是公平。持续到来的读者可能让写者长期等待；简单改成写优先后，持续写入又可能让读者长期等待。是否“碰巧公平”还会随标准库和平台变化。

首个并行正确版本使用每 shard 普通 `std::mutex`，以消除 reader/writer 两类准入策略并缩小正确性状态空间。标准 `std::mutex` 同样不保证 FIFO 或任意线程最终获得锁，因此这一步不提供公平性承诺。只有基准证明并发读确实受限时，再替换为 `QueueFairRwLock`。锁类型应藏在 `Shard` 内，Database API 不变。

### 11.2 `QueueFairRwLock` 的候选语义

这是一项需要单独实现、测试和评审的候选锁，不是当前代码已经具备的保证。它提供标准 RAII 所需接口：

```cpp
class QueueFairRwLock {
public:
    void lock();
    bool try_lock();
    void unlock();
    void lock_shared();
    bool try_lock_shared();
    void unlock_shared();
};
```

候选实现使用一个内部 `std::mutex`、一个 `condition_variable` 和 FIFO waiter 队列。每个 waiter 记录模式（read/write）和不可复用的请求身份；状态至少包含 `active_readers`、`writer_active` 和等待队列。准入谓词为：

- writer 只有在自己位于队首、没有活动 writer 且 `active_readers == 0` 时进入；
- reader 在没有活动 writer，且自己之前不存在等待 writer 时进入；因此队首连续 reader 自然合并为一个读批次；
- 新 reader 排在已经登记的 writer 后面，不能加入当前读批次；持续到来的 reader 不会绕过该 writer；
- 新 writer 排在已经登记的 reader 后面，后续 writer 不能绕过这些 reader；
- `try_lock()` 和 `try_lock_shared()` 仅在等待队列为空且当前状态允许时成功，不能借 try 路径插队；
- `unlock()` 和最后一个 `unlock_shared()` 重新计算可准入的队首批次并 `notify_all()`；所有等待都在谓词循环中处理虚假唤醒。

首版不提供 timed/cancellable lock，从而不存在等待中途遗留 queue node 的问题。未来若增加超时或取消，必须在内部互斥锁下原子移除 waiter，并在移除队首时重新唤醒后继。若使用数值 ticket，必须定义回绕处理；更简单的实现可直接以稳定 queue node 身份判断先后。

锁必须维持以下不变量：活动 writer 至多一个；writer 与 active reader 不同时存在；任何已准入 reader 之前都没有等待 writer；任何已准入 writer 都曾位于队首。多 shard guard 仍可能在持有低编号锁时等待高编号锁而形成 convoy，但统一升序保证它不会形成 shard 锁环。

在“等待线程最终能被 OS 调度、所有临界区有限结束、没有取消遗漏、try 路径不插队”的前提下，上述 FIFO 规则应使已登记的 reader/writer 在其前序有限批次结束后获得准入。它的目标是排除锁算法自身造成的无限饥饿，不承诺墙钟等待上限；正式实现需以状态机审查、模型/压力测试和 TSan 共同验证。不要使用忙等自旋：临界区可能执行内存分配、O(N) clone 或容器扩容。

### 11.3 锁不应升级或递归

- 写命令不能先 `lock_shared()` 查找，再尝试升级为 `lock()`；两个升级者会互等。
- 不使用 `recursive_mutex` 掩盖调用层次问题。
- 内部 helper 接受“调用者已持锁”的显式 tag 或保持 private，并在 Debug/TSan 测试中验证。
- RDB worker、网络线程和日志线程不能反向调用需要 shard 锁的路径。

## 12. 降低临界区长度

锁粒度不仅是“有多少把锁”，还包括“一次持锁做多少事”。按收益和复杂度排序：

1. **RESP 构造移到锁外。** 锁内只生成值类型结果。
2. **RDB 只在锁内复制快照句柄。** 编码、CRC 和磁盘操作全部锁外。
3. **长读固定不可变版本。** 大范围遍历和排序可在 `pinRead()` 后锁外执行。
4. **批量写只 detach 一次。** 避免重复引用计数检查和复制。
5. **对象先构造后发布。** `SET`、新 key 和编码转换所需的独立临时对象尽量在锁外准备，锁内校验状态后提交。
6. **按 shard 分散目录 rehash。** 单个 `unordered_map` 扩容不再阻塞全部 key。

若 profile 显示“大对象 detach 仍长期占用 shard 排他锁”，可以再增加乐观发布：

```text
共享锁下固定 old_handle + version
        -> 锁外 clone 并在私有 candidate 上执行命令
        -> 排他锁下比较 entry identity/version
        -> 未变化则发布；冲突则重试
        -> 超过有限重试次数后退化为锁内路径
```

这会引入重复复制和热点 key 重试，且命令返回值必须在每次重试时重新计算，因此只作为有指标支撑的后续优化，不进入首版。

## 13. 一致性与线性化语义

- 单 key 短读在线程持有共享锁、读取稳定对象期间线性化。
- pin 读在复制版本句柄时线性化，之后即使活动 key 被删除或替换，读者仍看到原版本。
- 原地写在 shard 排他临界区内线性化；读者只能在修改前或修改完成后进入。
- detach 写在新版本完成并成为活动 entry 时线性化；旧快照继续看到旧版本。
- 多 key 只读在取得最后一把相关 shard 锁后、释放第一把锁前的某一点线性化。多 key 写在全部修改成功后、释放第一把锁前提交；异常路径必须在发布任何修改前失败，或完成回滚后再释放锁。该原子性只约束访问相交 key/shard 的数据库操作，不涵盖网络响应或其他外部副作用。
- 完整数据库快照在线程同时持有全部 shard 共享锁的稳定区间内线性化。

同一连接的命令必须按请求顺序执行，或显式建立“前一条命令完成后才允许后一条开始”的依赖。首版最简单的规则是每个连接最多一个 in-flight 命令，完成后才调度下一条；request sequence 用于跨线程路由、校验和响应匹配。仅按 sequence 重排响应不够：若 `SET k new` 与后续 `GET k` 被两个 worker 反序执行，最终按序发送也无法修复 `GET` 已经读到旧值的语义错误。只有被证明结果与执行顺序无关的一组命令，才可做更细并行。锁只能保护共享数据，不能自动保持连接内命令顺序。

## 14. 异常、安全与资源边界

### 14.1 异常保证

- `CowPtr::detach()` 在 clone 或控制块分配失败时保持旧句柄不变。
- 新对象应在锁外或临时变量中完成构造，再以 move/swap 发布。
- ZSet 的一次更新跨两个容器；应调整插入顺序并在失败时回滚，不能依赖 COW 自动提供对象内部强异常安全。
- 后台保存失败只影响本次任务，活动数据库和旧 RDB 均保持可用。
- 所有 RAII guard 必须在异常路径释放锁；数据库 API 不暴露手工 unlock。

### 14.2 生命周期

- `ReadHandle` 和 `DatabaseSnapshot` 拥有强引用，不保存裸 `RedisObject*`。
- `DEL`、覆盖和 Database 析构不能使仍在编码的对象悬空。
- `Connection` 继续由所属 Reactor 的 `unique_ptr` 独占，不使用 COW。
- 快照任务退出或取消时按 RAII 释放全部句柄。

### 14.3 资源上限

- 快照任务队列有界，默认只允许一个活动任务。
- 记录并限制估算的 COW dirty bytes 和后台输出缓冲。
- 取消保存时应由 worker 协作检查 cancellation token，并安全删除临时文件。
- 不允许在持 shard 锁时等待队列空间；队列满应快速失败或在加锁前完成等待。

## 15. 分阶段实施路线

### P0：先修正现有所有权和异步入口

- 删除 `Server::db_` 或改为构造注入，确保全进程只有一个活动 Database。
- 信号处理改为 `signalfd`/self-pipe，由事件循环在安全点保存和退出。
- 为 pipeline 和连接读写增加事件预算；这解决的是调度饥饿。
- 建立当前单线程功能和延迟基线。

### P1：建立不可绕过的 COW 类型边界

- 新增 `include/mini_redis/core/CowPtr.hpp`。
- 给 `RedisObject` 和五种对象增加 `clone()`。
- 为 `Dict` 实现保留双表及 rehash 状态的深复制。
- 将 Database value 改为 `CowPtr<RedisObject>`，拆分 read/mutate API。
- 移除返回可变裸指针的后台 rehash API。

此阶段仍由单线程执行命令，便于先验证 COW 语义。

### P2：加入一致快照

- 新增 `DatabaseSnapshot`。
- RDB encoder 改为消费只读 snapshot range，而不是活动 `data_` 引用。
- 先让同步 `SAVE` 使用快照，验证所有对象和编码的隔离语义。
- 加入 clone 次数、字节数和快照生命周期指标。

### P3：后台 RDB

- 增加单 worker、有界队列、取消和任务状态。
- 主线程只建立/发布快照；worker 编码和落盘。
- 定义 `SAVE` 与新增 `BGSAVE` 的命令语义；首版重复 `BGSAVE` 返回 busy。
- 覆盖进程退出、保存失败、旧文件保留和内存阈值。

到这里，即使网络层改成多 Reactor，只要 Database 仍由唯一命令线程拥有，也不需要数据库锁。

### P4：并行命令的正确性脚手架

- 只有 profile 证明命令执行核已成为瓶颈时才开始。
- 先用一把 Database `std::mutex` 跑通并发、TSan 和线性化测试。
- 命令分类为只读、单 key 写、多 key，并把锁完全封装在 Database。
- 同一连接最多调度一个 in-flight 命令，或建立严格 predecessor-completion 依赖；sequence 只用于路由和校验。

### P5：固定 shard 与公平锁

- 把 key 空间拆成固定 shard。
- 引入统一多 shard guard 和严格升序锁规则。
- 初始每 shard 使用普通 mutex；读并行确有收益后切换经过状态机评审和压力测试的 queue-fair RW lock。
- 大范围读按阈值选择锁内读取或 pin 后锁外读取。

### P6：仅按指标继续细化

- 大对象锁外 clone + version 校验和有限重试。
- 对极大集合采用分块/页级 COW 或持久化数据结构。
- 若析构形成尾延迟，再做后台回收。
- 若单热点 key 是瓶颈，只能改命令/对象内部算法或做业务分区；继续增加 shard 无效。

## 16. 测试设计

### 16.1 `CowPtr` 与 clone 单元测试

- 空、拷贝、移动、自赋值和最后引用销毁。
- const API 的编译期约束，普通调用方无法取得可变 `RedisObject*`，不能绕过 Database 获得写访问。
- 唯一时不复制，共享后第一次写恰好复制一次，后续写不重复复制。
- clone/控制块分配失败时原句柄和值不变。
- 五种对象 clone 后值、类型和编码保持一致。
- Hash 在 `Dict` rehash 进行到一半时 clone，两个版本都能继续独立读写和完成 rehash。
- 多线程复制/销毁不同句柄，引用计数在 TSan 下无竞态。

### 16.2 快照隔离测试

建立快照后分别执行：

- `SET` 覆盖、新增 key、`DEL` 和跨类型覆盖；
- `HSET` 及 Hash 编码升级/rehash；
- `LPUSH/RPOP/LREM/LTRIM`；
- `SADD/SREM` 及 INTSET 到 STRSET 升级；
- `ZADD/ZREM`。

旧快照必须保持创建时的 key 集和值，活动数据库必须反映新值。未修改对象应保持相同 identity；被修改对象应分离。随后从快照写出 RDB、重新加载并验证五种类型。

### 16.3 锁与并发测试

- 多读者读取同一 key 和不同 shard。
- 多写者修改不同 shard，证明可以重叠执行。
- 多写者竞争同一 List/Hash/Set/ZSet，检查容器不变量。
- 读、写、删除和类型覆盖同一 key；读结果只能对应某个完整版本。
- `DEL a b` 与 `DEL b a`、未来跨 key 命令反序压力测试，设置超时检测死锁。
- `KEYS`、快照、`memory_usage` 与持续增删 key 并发。
- 后台 RDB 与全类型写入并发，反复加载每个产物并验证 CRC 和结构。
- queue-fair 锁在前述调度前提下，使持续读流中的已登记写者和持续写流中的已登记读者都能取得进展；同时验证 try-lock 不插队、虚假唤醒和队首批次切换。测试用 barrier/condition variable 控制阶段，不依赖随机调度。
- Debug CI 运行 ASan/UBSan；并发配置必须运行 TSan。

测试应设置 CTest timeout，避免死锁让 CI 永久挂起。对小状态空间可记录并发操作历史，使用简单线性化检查器确认结果存在合法串行顺序。

## 17. 基准与验收指标

### 17.1 负载矩阵

| 维度 | 建议取值 |
| --- | --- |
| 工作线程 | 1 / 2 / 4 / 8 |
| 读写比例 | 100/0、95/5、50/50、0/100 |
| key 分布 | 均匀、Zipf、单热点 |
| shard 数 | 1 / 16 / 64 / 256 |
| 对象 | 小 String、64 KiB String、边界 Hash/List/Set、大 ZSet |
| 快照期修改比例 | 0% / 1% / 10% / 100% key |
| 保存介质 | tmpfs 与真实目标磁盘分别测量 |

每轮至少记录：

- commands/s，p50、p95、p99、p99.9 和最大延迟；
- 每类锁的等待/持有时间、排队读者/写者峰值；
- 每 shard 请求分布、最热 shard 和冲突率；
- clone 次数、字节、耗时及按对象类型分布；
- 快照建立暂停、总保存耗时、前台写延迟；
- RSS/PSS 峰值、allocator bytes、临时文件大小；
- 乐观路径启用后的重试与 fallback 次数。

### 17.2 可重复执行协议

当前仓库还没有 `benchmarks/` 和 sanitizer CMake 开关；下列内容是实施 P1/P4 时必须一并补齐的工程门禁：

- 新增独立的 `mini_redis_cow_benchmark` 核心基准，直接调用 Database，排除网络噪声；另设 Linux 端到端驱动测量后台保存对客户端延迟的影响。
- 使用固定 seed 预生成 key、对象大小和操作序列；数据集在计时前装载，预热与正式样本之间重建到相同初态。
- 固定 Release 编译器、版本和编译参数；基线与候选版本使用同一机器、同一 allocator、同一 shard/线程配置。Linux 上用 `taskset` 固定 CPU；若不能锁定频率或隔离核心，必须把 governor、CPU 型号、负载和温度条件写入结果。
- 每个 case 先预热 3 轮、每轮 10 秒，再正式运行至少 10 轮、每轮 30 秒；基线和候选交替执行。以各轮中位数比较吞吐和延迟，同时报告 min/max 与离散程度；变异系数超过 3% 时不据此判定 5% 回退，应先排查噪声并重跑。
- 结果以 JSON Lines 固化，至少包含 commit、编译器、build type、机器/内核、seed、数据集、线程/shard 数、读写比例、每轮原始指标和失败计数。汇总表不能替代原始样本。
- tmpfs 用于隔离 COW/编码 CPU 成本，真实目标盘用于评估 `fsync` 和尾延迟；两组结果不能混合比较。

建议同时新增以下 CMake 选项：

```text
MINI_REDIS_ENABLE_ASAN_UBSAN
MINI_REDIS_ENABLE_TSAN
MINI_REDIS_BUILD_BENCHMARKS
```

ASan/UBSan 与 TSan 分开构建，不能组合到同一二进制。新增这些选项和测试目标后，Linux CI 使用：

```bash
cmake -S . -B build-asan -DBUILD_TESTING=ON \
  -DCMAKE_BUILD_TYPE=Debug -DMINI_REDIS_ENABLE_ASAN_UBSAN=ON
cmake --build build-asan -j
ctest --test-dir build-asan --output-on-failure --timeout 60

cmake -S . -B build-tsan -DBUILD_TESTING=ON \
  -DCMAKE_BUILD_TYPE=Debug -DMINI_REDIS_ENABLE_TSAN=ON
cmake --build build-tsan -j
ctest --test-dir build-tsan --output-on-failure --timeout 120
```

这些命令是实施后新增的 CI 契约，不代表当前 `CMakeLists.txt` 已支持对应选项。

### 17.3 正确性门槛

- 现有 8 个 CTest 全部通过。
- 新的 COW、快照和并发测试通过；ASan/UBSan/TSan 无报告。
- 后台生成的每个 RDB 都能重新加载，可选使用官方 `redis-check-rdb` 验证。
- 不存在可变裸指针越过 Database 锁/所有者边界。
- 锁顺序只有升序 shard 一种；源码检查不出现临时反序加锁。
- RDB 编码和文件 I/O 期间不持有任何 shard 锁。

### 17.4 性能门槛

绝对数字由目标机器建立基线，合入前至少满足：

- 没有快照、单线程负载下，COW 类型封装的吞吐回退不超过约 5%。
- 未修改数据集的快照不会深拷贝 value；clone 数应为 0。
- 修改 M 个已共享 key 时，clone 的对象数应接近 M，而不是总 key 数或 field/member 数。
- 后台保存期间不再出现完整编码和 `fsync` 时长级别的全局写暂停。
- 持续读/写压力下，两类等待者都持续取得进展；不存在等待队列只增不减。
- shard 方案在均匀 key 负载下相对全局锁有可重复扩展收益；若没有收益，应保留更简单的全局锁或单执行线程。

## 19. 最终建议

对这个仓库，推荐落地顺序是：

```text
修复信号重入与双 Database
        -> RedisObject::clone + Dict 深复制
        -> const-only CowPtr + Database 受控写入口
        -> 一致 DatabaseSnapshot
        -> 单后台 RDB worker
        -> profile 证明需要后再并行执行命令
        -> 全局 mutex 验证正确性
        -> 固定 shard + queue-fair RW lock
        -> 仅按数据决定是否做锁外 clone/容器级 COW
```

核心判断是：**COW 解决“读者如何继续安全读取旧版本”，锁解决“谁可以读取或发布活动版本”，调度预算解决“谁先获得 CPU”。三者职责不同，不能互相替代。**

近期最有价值的结果，是在仍保持单数据库写者的前提下，让 RDB 后台线程安全读取一致快照；这能获得 COW 的主要收益，同时避免过早承担多线程命令执行的锁竞争、死锁和顺序语义成本。
