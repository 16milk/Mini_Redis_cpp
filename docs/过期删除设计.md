# Mini_Redis_cpp 过期删除设计：懒删除与定时删除

> 设计日期：2026-08-26  
> 基线版本：`2c7994d`  
> 文档状态：已按本文第一版范围实现；后续扩展项仍以文中的非目标为准。
> 阅读说明：第 2 节记录实施前的基线问题，后续章节描述当前落地方案。

## 1. 执行摘要

当前项目没有运行态过期时间。`Database` 只保存 key 到对象的映射，所有命令由单个 `epoll` 事件线程串行执行；RDB 加载器虽然能识别官方过期 opcode 并跳过已经过期的 key，却会丢弃尚未到期 key 的 deadline，保存端也不写过期信息。

本设计采用“**懒删除保证语义正确，定时主动删除回收内存**”的组合：

```text
命令访问 key
    |
    v
expireIfNeeded(key, now) -------- 已到期 --------> 同步删除 value 与 TTL 元数据
    | 未到期
    v
执行原有读写语义

事件循环周期维护
    |
    v
activeExpireCycle(now, budget) --> 按 deadline 顺序、有预算地批量删除
```

核心决策如下：

1. TTL 是 **key 级元数据**，由 `Database` 管理，不放进 `RedisObject`。
2. 使用两个相互校验的索引：
   - `unordered_map<key, expire_at_ms>` 提供 O(1) 的懒过期判断；
   - `set<(expire_at_ms, key)>` 提供最近 deadline 查询与按序主动删除。
3. 所有键访问和删除收口到 `Database` 内部原语，过期判断必须发生在类型检查之前。
4. 主动删除仍在唯一数据库线程中执行，不创建后台删除线程，也不为每个 key 创建一个 timer。
5. `Server` 根据最近 deadline 和最大维护间隔计算 `epoll_wait` timeout；每轮删除同时受 key 数量和运行时间预算限制。
6. 运行态与 RDB 一律保存 **Unix epoch 毫秒绝对时间**；测试注入假时钟，不依赖 `sleep`。
7. 第一版提供 `EXPIRE`、`PEXPIRE`、`TTL`、`PTTL`、`PERSIST`，并为 `SET` 增加 `EX`/`PX` 选项。

这里的“定时删除”指事件循环周期执行的 active expiration cycle，而不是“每个 key 一个定时器”。前者内存有界、与现有单线程模型一致，并能通过预算控制事件循环尾延迟。

## 2. 当前实现与问题边界

### 2.1 数据与请求路径

`Database` 当前只有一张顶层表：

```cpp
std::unordered_map<std::string, std::shared_ptr<RedisObject>> data_;
```

见 `include/mini_redis/core/Database.hpp:75`。多数 String、Hash、List、Set 和 ZSet 操作会先调用 `lookupKey()`，见 `src/core/Database.cpp:331`；这为集中接入懒删除提供了合适边界。

但以下路径直接访问 `data_`，不能只修改 `lookupKey()`：

| 路径 | 当前行为 | TTL 改造要求 |
| --- | --- | --- |
| `keyExists()` | 直接 `data_.count()` | 先执行懒过期 |
| `exists()` | 直接 `data_.count()` | 对每个参数按同一 `now` 判断 |
| `getAllKeys()` | 直接遍历 `data_` | 不返回逻辑已过期 key，并安全处理迭代器 |
| `del()` | 直接 `data_.erase()` | 同时移除两个 TTL 索引 |
| List/Set/ZSet 清空 | 多处直接 `data_.erase()` | 统一走 `eraseKey()` |
| `saveRdb()` | 直接把 `data_` 交给编码器 | 过滤已过期 key，并保存未来 deadline |
| `memory_usage()` | 只统计 value map 和对象 | 明确改成物理内存口径并计入 TTL 索引 |

### 2.2 当前执行模型

请求路径为：

```text
epoll_wait
  -> Connection::readFromSocket
  -> RespParser::parse
  -> CommandHandler::execute
  -> Database / RedisObject
  -> Connection write buffer
```

`Server::run()` 串行处理 ready fd，`Connection::readFromSocket()` 会一直读到 `EAGAIN`，`process_client_input()` 又会同步执行连接缓冲中的所有完整命令，见 `src/net/Connection.cpp:13`、`src/net/Server.cpp:117` 和 `src/net/Server.cpp:141`。当前没有命令工作线程、数据库锁或线程池。持续写入的客户端可能同时在“读 socket”和“执行 pipeline”两个阶段长期占用事件线程。

因此第一版主动删除应继续服从单线程所有权。若单独启动删除线程，它会和事件线程并发修改 `unordered_map` 及对象生命周期；给局部位置补锁也无法自动保证 `DEL`、对象清空、RDB 和 TTL 索引之间的一致性。

### 2.3 当前事件循环不能驱动定时任务

`epoll_wait(..., -1)` 会无限等待，见 `src/net/Server.cpp:156`。服务器无网络流量时，没有机会主动清理过期 key。仅依赖“每次收到命令后顺便清理”仍然是懒删除，不满足定时回收内存的目标。

### 2.4 当前存在两份 Database

`main.cpp` 中的全局 `g_db` 才是 `CommandHandler` 实际操作的数据库，但 `Server` 自己还持有一份未使用的 `Database db_`，见 `src/main.cpp:9` 和 `include/mini_redis/net/Server.hpp:25`。如果直接在 `Server::run()` 中对成员 `db_` 调用主动删除，会清理错误的数据库。

TTL 调度接入前必须先收敛数据库所有权，使命令、主动删除和持久化操作同一个实例。

### 2.5 RDB 只实现了半条过期链路

当前加载器识别 `RDB_OPCODE_EXPIRETIME` 与 `RDB_OPCODE_EXPIRETIME_MS`，并在加载时跳过已过期对象，见 `src/persistence/Rdb.cpp:997` 和 `src/persistence/Rdb.cpp:1019`。但未来 deadline 在对象放入结果 map 后被丢弃，见 `src/persistence/Rdb.cpp:1060`。

保存端把 `RESIZEDB` 的 expire 数量固定写成 0，也从不写 expire opcode，见 `src/persistence/Rdb.cpp:917`。所以只实现内存 TTL 会导致重启后 TTL 消失，不能作为完整功能交付。

## 3. 目标与非目标

### 3.1 目标

- deadline 到达后，任何命令都不能再观察到旧值，即使主动清理尚未运行。
- 空闲服务器也能主动释放过期 key；大量 key 同时到期时不长时间阻塞网络事件循环。
- String、Hash、List、Set、ZSet 共享一致的 key 级 TTL 语义。
- 覆盖、删除、容器清空、取消 TTL 和同名 key 重建后，不残留会误删新值的定时项。
- 对外命令语义与 Redis 的基础 TTL 行为一致。
- RDB 保存未来 deadline，重启后按原绝对时间继续过期，而不是重新开始一段完整 TTL。
- 单元测试使用可控时钟，精确覆盖 deadline 边界且不引入慢速、易抖动的真实等待。
- 数据结构和调度接口为后续统一 maintenance（如渐进式 rehash）保留扩展点。

### 3.2 非目标

- 第一版不实现 `EXPIREAT`、`PEXPIREAT`、`EXPIRE NX|XX|GT|LT`、`SET EXAT|PXAT|KEEPTTL`。底层绝对毫秒模型应允许后续无结构性改造地增加它们。
- 不实现每 key 一个线程、一个 `timerfd` 或一个回调对象。
- 不新增后台删除线程，不在本阶段引入数据库锁。
- 不实现 Redis 的随机采样 active-expire 算法；本项目选择有序 deadline 索引，以换取确定性清理与更简单的下一唤醒时间计算。
- 不承诺物理删除恰好发生在 deadline 所在的毫秒。逻辑可见性由懒删除精确保证，物理清理由事件循环调度，允许有受控延迟。
- 不解决超大对象析构本身造成的单次停顿；若基准证明这是问题，再设计 lazy-free/异步回收。
- 不在本设计中实现多线程或分布式 TTL。未来分布式模式必须由 leader 提交版本化过期记录，不能让副本按各自墙上时间独立删除。

## 4. 对外命令与可见语义

### 4.1 第一版命令范围

| 命令 | 语义 | 返回值 |
| --- | --- | --- |
| `EXPIRE key seconds` | 设置相对秒级 TTL | 设置或立即删除成功为 `1`；key 不存在为 `0` |
| `PEXPIRE key milliseconds` | 设置相对毫秒级 TTL | 同上 |
| `TTL key` | 查询剩余秒数 | 不存在 `-2`；永久 key `-1`；否则返回剩余秒数 |
| `PTTL key` | 查询剩余毫秒数 | 不存在 `-2`；永久 key `-1`；否则返回剩余毫秒数 |
| `PERSIST key` | 移除现有 TTL | 成功移除为 `1`；不存在或本来无 TTL 为 `0` |
| `SET key value EX seconds` | 写入 String 并设置秒级 TTL | 成功 `+OK` |
| `SET key value PX milliseconds` | 写入 String 并设置毫秒级 TTL | 成功 `+OK` |

`SET` 第一版只允许无选项、一个 `EX` 或一个 `PX`；选项大小写不敏感。重复、冲突、多余选项均返回语法错误。参数必须是完整十进制有符号整数，并在换算和 `now + duration` 前检查溢出。

边界规则：

- `expire_at_ms <= now_ms` 即视为已过期。
- `EXPIRE`/`PEXPIRE` 的 timeout 小于等于 0 时，如果 key 存在则立即删除并返回 `1`；不存在返回 `0`。
- `SET ... EX/PX` 的 timeout 小于等于 0 是参数错误，命令不得修改原值。
- `PTTL` 返回精确的非负剩余毫秒数。
- `TTL` 按 Redis 的毫秒到秒规则计算：`(remaining_ms + 500) / 1000`。
- 一条命令只读取一次 `now_ms`；多 key 命令中的所有参数共享这个时间点，避免同一命令内部跨越 deadline 后产生不一致结果。

### 4.2 各类访问对过期 key 的处理

| 访问路径 | 已过期 key 的行为 | 活着且带 TTL 的 key |
| --- | --- | --- |
| `GET/HGET/LINDEX/LRANGE/LLEN/...` | 当作不存在 | 正常读取，TTL 不变 |
| `HSET/LPUSH/RPUSH/SADD/ZADD` | 先删除旧 key，再按不存在创建新对象 | 修改对象成员，保留原 TTL |
| `LPOP/RPOP/LREM/LTRIM/SREM/ZREM` | 当作不存在 | 修改后对象若为空，删除 key 和 TTL |
| `SET key value` | 覆盖为新值 | 无选项覆盖时清除旧 TTL |
| `SET ... EX/PX` | 覆盖并安装新 TTL | 原值与原 TTL 一起被替换 |
| `DEL` | 不计入删除数，但清理物理残留 | 删除 value 和 TTL，计数 `1` |
| `EXISTS` | 计数 `0` | 计数 `1`；重复参数仍逐个计数 |
| `KEYS *` | 不出现在结果中 | 正常返回 |
| 类型检查 | 先过期，再判断类型 | 按原逻辑判断 |
| `SAVE` | 不写入 RDB | 写入对象；有 TTL 时同时写 deadline |

过期判断必须先于类型检查。例如旧 Hash 已过期后执行 `GET`，结果应是 null，而不是 `WRONGTYPE`；执行 `LPUSH` 时应创建一个新 List，而不是因为物理残留的 Hash 报错。

## 5. 数据模型

### 5.1 TTL 属于 key，而不是对象

建议在 `Database` 增加：

```cpp
using UnixMillis = std::int64_t;
using ExpireIndex = std::unordered_map<std::string, UnixMillis>;
using ExpireSchedule = std::set<std::pair<UnixMillis, std::string>>;

std::unordered_map<std::string, std::shared_ptr<RedisObject>> data_;
ExpireIndex expires_;
ExpireSchedule expire_schedule_;
```

TTL 不进入 `RedisObject`，理由如下：

- Redis 的过期单位是整个 key，而不是 Hash field、List element 或 ZSet member。
- `SET` 可以用新对象覆盖旧对象；key 元数据必须独立决定清除或替换 TTL。
- 主动删除需要跨所有对象类型按 deadline 统一排序。
- RDB 的 expire opcode 位于 key/object 记录之前，本身也是顶层元数据。

### 5.2 双索引职责

```text
data_
  key ---------------------------> RedisObject
   |
   +--> expires_[key] -----------> absolute Unix milliseconds
                     |
                     +-----------> expire_schedule_[(deadline, key)]
```

| 结构 | 主要用途 | 平均/最坏复杂度 |
| --- | --- | --- |
| `data_` | 查找对象 | 平均 O(1) |
| `expires_` | 单 key 懒过期、TTL 查询 | 平均 O(1) |
| `expire_schedule_` | 最近到期项、主动删除 | 首项 O(1)，插入/删除 O(log E) |

其中 `E` 是带 TTL 的 key 数。`std::set<pair<deadline,key>>` 在同 deadline 下按 key 排序，行为确定；更新 TTL 时可用旧 deadline 精确删除旧节点。

不采用只有 `priority_queue` 的方案。堆无法按 key 删除旧 deadline，通常只能保留 stale node 并在弹出时校验；一个热点 key 被反复续期时，旧节点可能长期累积。当前项目更需要简单、可验证和内存有界，而不是略低的常数开销。

不采用每轮扫描整个 `expires_` 的方案。它会让没有到期 key 的维护周期仍为 O(E)，并且无法直接计算下一次唤醒时间。

### 5.3 必须长期成立的不变量

1. `expires_` 中的每个 key 必须存在于 `data_`。
2. `expires_[key] = deadline` 当且仅当 `expire_schedule_` 中存在唯一的 `(deadline, key)`。
3. `data_` 中的 key 可以没有 TTL；`expire_schedule_` 中不能存在孤儿节点。
4. `deadline <= now` 的 key 在逻辑上不存在，即使它尚占用物理内存。
5. 删除 key 必须原子地维护三个容器的逻辑关系，不能只删除 value 或只删除 TTL。
6. 同名 key 删除后重建时，旧 deadline 绝不能影响新值。
7. 所有运行态 deadline 使用非负、有符号 64 位 Unix 毫秒；外部无符号值进入前必须做范围检查。

Debug 构建可提供低频的 `validateExpirationIndexes()`，验证前 3 条不变量；不要在每个生产命令后做 O(E) 全量校验。

### 5.4 内存取舍

带 TTL 的 key 会额外出现在哈希索引和有序索引中，首版会保存两份 key 字符串。这个开销换取了：

- 稳定的 O(1) 懒判断；
- O(log E) 的精确续期/取消；
- 无 stale heap node；
- O(1) 获取最近 deadline。

若未来数百万 TTL key 的内存基准表明字符串复制不可接受，可再引入稳定 key handle、interning 或 intrusive 节点；首版不使用引用 `unordered_map` key 的迭代器/指针，因为 rehash 会使迭代器失效并增加生命周期风险。

## 6. Database 内部 API 与生命周期收口

建议引入以下内部原语；命名可以随实现微调，但职责不能散落：

```cpp
using NowFunction = std::function<UnixMillis()>;

bool expireIfNeeded(const std::string& key, UnixMillis now_ms);
bool eraseKey(const std::string& key);
bool setExpireAt(const std::string& key, UnixMillis deadline_ms, UnixMillis now_ms);
bool clearExpire(const std::string& key);

std::shared_ptr<RedisObject> lookupKey(const std::string& key, UnixMillis now_ms);
void storeKey(const std::string& key, std::shared_ptr<RedisObject> object,
              ExpirePolicy policy);

ExpireCycleResult activeExpireCycle(UnixMillis now_ms,
                                    std::size_t max_keys,
                                    std::chrono::microseconds max_runtime);
std::optional<UnixMillis> nextExpireAt() const;
```

### 6.1 `eraseKey`

统一删除顺序：

1. 在 `expires_` 查旧 deadline；
2. 若存在，删除 `expire_schedule_` 中的 `(deadline, key)`；
3. 删除 `expires_` 条目；
4. 删除 `data_` 条目并返回它原先是否存在。

`DEL`、懒删除、主动删除、立即过期、`LPOP/RPOP/LREM/LTRIM/SREM/ZREM` 清空对象等路径全部调用它。实现完成后，`Database.cpp` 中除受控加载/销毁逻辑外不应再散落 `data_.erase(key)`。

### 6.2 `expireIfNeeded` 与 `lookupKey`

伪代码：

```text
expireIfNeeded(key, now):
    expiry = expires_.find(key)
    if expiry is absent or expiry.deadline > now:
        return false
    eraseKey(key)
    expired_keys_total++
    return true

lookupKey(key, now):
    if expireIfNeeded(key, now):
        return null
    return data_.find(key)
```

懒删除会修改数据库，因此当前 `get()`、`hget()`、`lindex()`、`exists()`、`getAllKeys()`、`checkType()` 等带 `const` 的逻辑读取接口应改为非 `const`。不建议把 `data_` 和 TTL 索引声明为 `mutable` 来隐藏副作用。命令处理器本来持有非 const `Database&`，显式表达修改更符合真实语义。

### 6.3 `setExpireAt` 与 `clearExpire`

`setExpireAt` 的步骤：

1. 先对 key 做懒过期；不存在则返回 false。
2. `deadline <= now` 时调用 `eraseKey()`，返回 true。
3. 若新旧 deadline 相同，直接返回 true。
4. 先向 schedule 插入新 `(deadline,key)`；分配失败时旧状态保持不变。
5. 新建 TTL 时再向 `expires_` 插入；若失败则回滚刚插入的 schedule 节点。已有 TTL 只需更新整数值，不产生新的 map 节点。
6. 最后删除 schedule 中的旧 `(deadline,key)`。单线程执行期间允许短暂同时存在新旧两个 schedule 节点，但方法返回时必须恢复唯一映射。

这套顺序至少为 TTL 元数据更新提供强异常保证。`SET ... EX/PX` 还要把 value 替换与 TTL 安装封装成同一个 Database 操作：先完成参数校验和所有可能失败的节点准备，再提交对象与 deadline；如果项目不打算从 `bad_alloc` 恢复，则应明确 fail-fast，但仍不能捕获异常后带着破坏的不变量继续服务。

`clearExpire` 精确删除 schedule 和 hash 中的旧记录；只有确实移除 TTL 时返回 true。`PERSIST` 先懒过期，再调用该接口。

### 6.4 `storeKey` 的 TTL 策略

覆盖语义不能依赖调用者“记得顺便删 TTL”。建议显式区分：

```cpp
enum class ExpirePolicy { Clear, Preserve };
```

- 普通 `SET` 使用 `Clear`。
- `SET ... EX/PX` 先完整解析并校验参数，再以 `Clear` 覆盖 value 并安装新 deadline；在单线程中整个过程对其他命令不可见。
- 对活着的 Hash/List/Set/ZSet 做成员修改，不调用覆盖式 `storeKey`，自然保留 TTL。
- 复合对象不存在时创建新 key，不应继承任何历史 TTL。
- RDB 恢复使用专用加载路径，同时安装已验证的 value 与 deadline，不复用容易清 TTL 的普通 `SET` 路径。

### 6.5 全量遍历接口

`KEYS *` 本身就是 O(N)，应对整个结果执行严格的逻辑存活过滤。不能在 range-for 遍历 `data_` 时调用会 erase 当前元素的通用 `eraseKey()`；可选实现是显式迭代器安全推进，或者先收集待删 key、遍历结束后统一删除。

`SAVE` 必须在一个固定 `snapshot_now` 下过滤全部条目。即使主动删除有预算限制，RDB 也不得写入 `deadline <= snapshot_now` 的 key。

`memory_usage()` 定义为物理内存估算：它可以包含“已逻辑过期、尚未来得及主动回收”的对象，并应增加两个 TTL 索引的估算开销。若以后需要逻辑 key 数或逻辑数据大小，应另设指标，避免在只读统计函数里偷偷执行无预算的全量删除。

## 7. 懒删除流程

以 `HSET key field value` 为例：

```text
CommandHandler::handleHSet
    -> Database::hset
        -> now = clock()             # 本命令固定时间点
        -> lookupKey(key, now)
            -> expires_ 无记录       # 永久 key
            -> 或 deadline > now     # 未到期
            -> 或 eraseKey(key)      # 已到期，返回不存在
        -> 不存在：创建新 Hash，无 TTL
        -> 存在：检查类型并修改，保留 TTL
```

懒删除是正确性的最终兜底：

- 主动周期延迟执行，不会让过期值重新可见；
- 服务器一直忙于网络事件，不会让过期值重新可见；
- 测试或嵌入场景只使用 `Database`、不启动 `Server`，仍有正确语义；
- 系统时钟突然向前跳，下一次键访问会立即按新时间判断。

同一条多 key 命令应缓存一次 `now`。例如 `EXISTS a a b` 中，若 `a` 在命令开始时存活，则重复参数都计数；若命令开始时已到期，则第一次检查删除它，后续检查仍为不存在。

## 8. 定时主动删除流程

### 8.1 删除算法

`activeExpireCycle` 从 `expire_schedule_.begin()` 开始，只处理已经到期的前缀：

```text
activeExpireCycle(now, key_budget, time_budget):
    started = steady_clock.now()
    examined = 0
    deleted = 0

    while schedule is not empty:
        (deadline, key) = copy of first schedule entry
        if deadline > now:
            break
        if examined == key_budget or elapsed >= time_budget:
            break

        examined++
        verify expires_[key] still equals deadline
        eraseKey(key)
        deleted++

    return {examined, deleted,
            more_due = first deadline <= now,
            next_deadline = first deadline if any}
```

必须先复制首节点的 deadline 和 key，再调用 `eraseKey()`；不能持有 `set` 节点内字符串的引用并在节点被删除后继续使用它。虽然双索引正常状态下不应出现 stale node，主动周期仍应校验 `expires_[key] == deadline`：Debug 构建直接报告不变量破坏，Release 构建安全移除孤儿 schedule 节点，不能误删 value。

对外 deadline 使用 system/wall clock；限制本轮运行时长必须使用 `steady_clock`，避免墙上时钟跳变让预算失效。一次 cycle 使用固定的 `now`，执行期间新到期的 key 留到下一轮。

初始默认值建议：

| 参数 | 默认值 | 说明 |
| --- | ---: | --- |
| 最大 maintenance 间隔 | 100 ms | 空闲时的主动回收精度上界之一 |
| 每轮过期 key 上限 | 64 | 防止同刻过期风暴独占事件线程 |
| 每轮过期时间预算 | 1 ms | 每删除一个 key 后检查；不能中断单个大对象析构 |
| pipeline 中维护间隔 | 每 64 条命令 | 防止持续可读连接让维护永久饥饿 |
| 单连接每轮读取预算 | 64 KiB 或 16 次 read | 防止持续发送者让 `readFromSocket()` 永不返回 |

这些值应集中为 `ServerConfig` 或具名常量，后续根据 p99 延迟、过期积压和 CPU 占用调整，不能散落魔法数字。

### 8.2 为什么仍然需要预算

如果十万个 key 在同一毫秒到期，一次全部删除会同步析构十万个对象，期间服务端不能 accept、read 或 write。主动删除的职责是逐步回收物理内存，而不是牺牲前台延迟追求零积压。

预算耗尽但仍有到期项时，结果中的 `more_due` 置为 true；事件循环下一轮使用 0 ms timeout，在每批过期工作之间继续轮询并处理网络事件。

### 8.3 事件循环集成

推荐先使用动态 `epoll_wait` timeout，不引入 `timerfd`：

```text
loop:
    if maintenance is due:
        run bounded activeExpireCycle
        run separately-budgeted rehash maintenance

    timeout = min(
        time until next maintenance tick,
        time until nearest expire deadline,
        max_maintenance_interval
    )
    if expired backlog remains:
        timeout = 0

    epoll_wait(timeout)
    process ready fds with command budgets
    periodically run a small maintenance slice inside deep pipelines
```

timeout 计算必须：

- 将过去的 deadline 截断为 0；
- 将大于 `INT_MAX` 的差值安全截断；
- 即使没有 TTL，也至多等待 `max_maintenance_interval`，为时钟跳变、rehash 和未来维护任务保留唤醒点；
- 在 `EINTR` 后回到循环顶部重新读时钟，而不是沿用旧 timeout。

动态 timeout 只保证“没有网络事件时会醒来”。持续 I/O 或单个深 pipeline 仍可能让维护饥饿，因此需要同时限制：单次 socket 读取字节数/系统调用数、每个连接连续执行的命令数/时间，以及一轮 ready fd 的总处理时间。读预算耗尽或用户态缓冲中仍有完整命令时，把连接放入本地 ready queue；队列非空时下一轮不能无限阻塞。每到维护 deadline，或每执行固定数量命令，就插入一个小型 maintenance slice。完整的公平调度可沿用《网络性能分析与升级建议》的方案。

原有 `get_rehashing_dicts()` 会把内部裸 `Dict*` 交给调用方；若取得指针后主动过期或命令覆盖对应 key，指针会悬空。实现已将其替换为 `Database::advanceRehash(budget)`，由数据库在所有权范围内完成遍历和推进，不让内部可变指针跨维护步骤逃逸。过期清理和 rehash 使用独立预算，避免任一任务吃掉另一任务的全部时间。

### 8.4 数据库所有权改造

建议让 `Server` 持有数据库引用并在内部构造命令处理器：

```cpp
class Server {
public:
    Server(Database& db, int port = 6380);

private:
    Database& db_;
    CommandHandler command_handler_;
};
```

`main()` 创建唯一 `Database` 后注入 `Server`。请求执行、主动删除和 `SAVE` 都走该实例，并移除 `Server.cpp` 中的 `extern g_cmd_handler`。

当前信号处理函数直接执行 iostream、RDB 保存和 `exit()`，不是 async-signal-safe。TTL 改造不应继续扩大这条路径；后续应让信号处理器只写 self-pipe/eventfd 或设置可安全观察的通知，由事件循环在命令边界保存并退出。

## 9. 时钟设计

### 9.1 两类时间不能混用

| 时间来源 | 用途 | 是否持久化 |
| --- | --- | --- |
| `system_clock` / Unix epoch ms | deadline、懒过期、TTL/PTTL、RDB | 是 |
| `steady_clock` | 单轮维护耗时、命令处理时间预算 | 否 |

不能把 `steady_clock::time_since_epoch()` 写入 RDB；它只在当前进程中单调，重启后没有可比较意义。

### 9.2 可注入时钟

`Database` 接收一个 `NowFunction`，生产默认实现返回 `system_clock` 的 Unix 毫秒，测试传入捕获可变整数的 lambda：

```cpp
UnixMillis fake_now = 1'700'000'000'000;
Database db(/* disable_rdb_load = */ true, [&] { return fake_now; });

db.set(...);
db.expire(...);
fake_now += 1000;
// 精确断言 deadline 边界，不 sleep。
```

RDB 编解码器不能自行调用 `std::time()`；保存和加载都接收调用方固定下来的 `now_ms`。这也修复当前加载器只有秒精度、边界最多偏差近 1 秒的问题。

### 9.3 墙上时钟跳变

Redis 风格的绝对 deadline 意味着：

- 时钟向前跳：key 可能立即过期；懒访问和下一个维护 tick 会处理它。
- 时钟向后跳：过期会相应延后，这是绝对墙上时间语义的自然结果。
- 根据最近 deadline 计算过长睡眠并不安全，所以事件循环仍设置 100 ms 的最大维护间隔。

## 10. RDB 持久化设计

### 10.1 API 边界

当前 `RdbEncoder` 只传递 object map，无法表达 TTL。建议引入共享类型别名和加载结果：

```cpp
using ObjectMap = std::unordered_map<std::string, std::shared_ptr<RedisObject>>;
using ExpireMap = std::unordered_map<std::string, UnixMillis>;

struct RdbLoadResult {
    ObjectMap objects;
    ExpireMap expires;
};
```

接口调整为等价于：

```cpp
static bool saveToFile(const std::string& filename,
                       const ObjectMap& objects,
                       const ExpireMap& expires,
                       UnixMillis snapshot_now_ms);

static RdbLoadResult loadFromFile(const std::string& filename,
                                  UnixMillis load_now_ms);
```

加载完成后，`Database` 移入两张哈希表，并从 `expires` 重建 `expire_schedule_`。构造过程要验证 TTL key 一定存在于 objects。

### 10.2 保存规则

一次 `SAVE` 在开始时只读取一次 `snapshot_now_ms`，随后：

1. 统计 `deadline > snapshot_now_ms` 的存活 key 数和其中带 TTL 的 key 数；
2. 将这两个实际数量写入 `RESIZEDB`；
3. 跳过 `deadline <= snapshot_now_ms` 的对象；
4. 有 TTL 的对象先写 `RDB_OPCODE_EXPIRETIME_MS`；
5. 以 8 字节 little-endian 写入绝对 Unix 毫秒；
6. 紧接着写原有 object type、key 和 value；
7. 保留当前 CRC64、临时文件、`fsync`、原子 `rename` 流程。

RDB 编码无需为了过滤已过期项而修改在线数据库。当前 `SAVE` 本来就是同步命令；在同一事件线程中遍历一致的 `data_`/`expires_` 即可。未来若实现 COW 后台快照，object 版本和 TTL map 必须在同一个快照点一起捕获。

### 10.3 加载规则

- `EXPIRETIME` 秒时间戳安全乘以 1000，检查溢出。
- `EXPIRETIME_MS` 的 `uint64_t` 值必须不超过 `INT64_MAX`。
- 解码对象后，`deadline <= load_now_ms` 的条目不进入结果。
- 未来 deadline 同对象一起返回，不能像当前实现一样丢弃。
- pending expire 只绑定紧随其后的一个对象；对象结束后必须清零。
- EOF 前悬空 expire、同一对象重复 expire、非法元数据顺序等输入应明确报错。
- DB 0 之外仍沿用当前“不支持并拒绝”的策略。

过期时间是绝对值，因此 RDB 离线 30 秒后再加载，剩余 TTL 应少 30 秒；不能把保存时的剩余时长重新加到启动时刻。

## 11. 并发与未来演进约束

第一版中，所有 `data_`、`expires_`、`expire_schedule_` 修改都由事件循环/命令线程完成，不需要 mutex。`shared_ptr` 只管理对象生命周期，不能让三个容器自动具备并发安全性。

未来若引入后台 RDB、并行命令或分片 actor，必须继续满足：

1. value 与 deadline 属于同一个 key 状态，发布、覆盖和快照必须一致。
2. 主动删除只能由拥有该数据库写权限的执行器发起。
3. 不能让后台线程直接遍历并修改活动的三个容器。
4. 分布式副本不能按自己的 wall clock 独立删 key；leader 应把绝对 deadline 写入复制日志，并在到期时提交 `ExpireIfVersion` 一类的条件删除。

这些约束与《读写并发、写时复制与锁设计》及《分布式Redis架构设计》的演进方向一致。

## 15. 推荐实施顺序

1. **收敛所有权**：让 `Server`、`CommandHandler`、maintenance 和持久化共享唯一 `Database`。
2. **注入时钟**：建立 Unix 毫秒时间类型和 fake clock，暂不接网络定时调度。
3. **收口键生命周期**：加入 `eraseKey`、`expireIfNeeded`、`setExpireAt`、`clearExpire`，替换所有直接删除。
4. **完成懒删除**：让全部单 key、多 key、类型检查和全量遍历路径获得一致逻辑。此阶段即使没有主动周期，也不能读到过期值。
5. **接入命令**：实现 EXPIRE/PEXPIRE/TTL/PTTL/PERSIST 与 SET EX/PX，先通过 fake-clock 测试。
6. **完成 RDB 闭环**：保存和加载未来 deadline，重建 schedule，通过 round-trip 和兼容测试。
7. **接入主动删除**：动态 epoll timeout、双重预算、积压续跑和 pipeline 维护点。
8. **补齐治理**：统计指标、压力/公平性测试、sanitizer 与文档状态更新。

这个顺序先建立语义正确性，再解决物理内存回收；任意中间阶段都不会因为主动调度暂未接入而暴露过期值。

## 16. 验收标准

实现可认为完成，需同时满足：

1. 所有命令在 `deadline <= now` 时都把 key 当作不存在，且判断先于类型检查。
2. 空闲服务器无需后续访问，也会在最大维护间隔内开始物理删除到期 key；若存在积压，则按预算逐轮下降。
3. 同刻大批过期不会让一次 active cycle 超出 key 预算；时间预算在单个对象析构边界之间生效。
4. 覆盖、DEL、PERSIST、容器清空和同名重建后，`data_`、`expires_`、`expire_schedule_` 不变量成立。
5. 不新增并发写数据库的线程，不依赖 mutex 掩盖所有权问题。
6. RDB 保留未来绝对 deadline，过滤已经到期的 key，`RESIZEDB` 计数正确，官方 checker 可接受输出。
7. 核心 TTL 测试不使用真实 sleep；deadline 等于当前时间、负值与溢出均有覆盖。
8. 持续 I/O/深 pipeline 下主动删除不会永久饥饿，过期积压可逐轮下降。
9. 当前全部回归测试继续通过，新增测试在支持的平台上稳定通过。
10. `docs/仓库功能分析.md` 在功能真正实现后同步更新，不提前把设计提案描述成已交付能力。

## 17. 主要风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 漏改直接 `data_` 访问 | 已过期 key 泄漏或 TTL 残留 | 收口 helper、`rg` 审计、随机不变量测试 |
| 同一 key 反复续期 | schedule 膨胀或旧 deadline 误删新值 | `set` 精确移除旧 pair；双索引一致性校验 |
| 大量 key 同刻过期 | Reactor 长暂停 | key 数 + steady-clock 时间双预算，积压时零 timeout 续跑 |
| 深 pipeline | maintenance 饥饿 | 命令预算/维护插入点，后续 ready queue |
| wall clock 跳变 | 提前或延后过期 | 明确绝对时间语义、最大 100 ms tick、每次重读时钟 |
| RDB 仅保存 value | 重启后 TTL 消失 | load/save API 同时携带 expire map，往返测试 |
| `KEYS` 遍历时删除 | 迭代器失效 | 显式迭代器或先收集后删除 |
| 大对象同步析构 | 单次删除仍可能尖峰 | 首版记录 cycle 延迟；超标后设计 lazy-free |
| 双 Database 所有权 | 定时任务清理错误实例 | TTL 接入前完成构造注入并移除全局 handler 路径 |
| 信号处理期间 SAVE | 重入、容器中间态和未定义行为 | 信号只通知，事件循环在安全点保存退出 |

总体上，该方案把“何时不可见”和“何时释放内存”分开：懒删除提供严格的逻辑过期边界，有预算的定时主动删除负责最终回收。双索引让两条路径都能高效执行，同时保持当前单线程数据库最重要的简单性和命令原子性。

## 18. 实施结果（2026-08-26）

第一版已完成：

- `Database` 已加入 `expires_` 与 `expire_schedule_` 双索引、统一键删除入口、懒删除、主动删除、统计和可注入时钟。
- 命令层已接入 `EXPIRE`、`PEXPIRE`、`TTL`、`PTTL`、`PERSIST` 与 `SET EX/PX`。
- RDB 已能保存并恢复绝对毫秒 deadline，保存和加载都会过滤已经到期的 key；损坏的默认 RDB 会阻止服务以空库继续启动。
- `Server` 已改为使用注入的唯一 `Database`，通过动态 `epoll_wait` timeout 调度主动过期；连接读、命令执行和写均有预算，并使用输入/输出水位与本地 ready queue 控制公平性。
- 信号处理器只设置 `sig_atomic_t` 标志，事件循环退出后再保存 RDB。
- 新增确定性过期测试，并扩展命令、RDB 和网络 I/O 回归测试。

当前环境没有 `cmake`，因此使用 Apple Clang 21 按 CMake 中的源文件集合等价构建。9 个测试可执行文件全部通过；expiration、command semantics、RDB round-trip、RDB compatibility 和 network I/O 关键路径还通过了 AddressSanitizer 与 UndefinedBehaviorSanitizer。目标服务端依赖 Linux `epoll`，在 macOS 上通过临时声明桩完成语法与类型检查，仍需在 Linux CI/主机执行真实服务端集成测试。
