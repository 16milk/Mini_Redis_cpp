# Mini Redis 简历内容

> 使用说明：本文按照分布式方案全部完成后的目标状态撰写。正式投递前，应逐条确认对应功能已经实现，并通过多节点、故障恢复和一致性测试；尚未完成的能力不应作为已落地成果使用。

## 一、简历正文

### Mini Redis｜分布式内存键值存储系统

**技术栈：** C++17、Linux、Epoll、Reactor、RESP、Raft、WAL、Snapshot、RDB、CMake

**项目介绍：**

从零设计并实现兼容 Redis 核心协议与数据结构的分布式内存键值存储系统。系统采用 Redis Cluster 风格的 16384 个 Hash Slot 完成数据分片，每个逻辑分片由独立的三副本 Raft Group 提供强一致复制与故障转移，并通过元数据 Raft Group 管理节点、分片、Slot 所有权和在线迁移状态。项目支持 String、Hash、List、Set、ZSet 五种数据类型、常用 Redis 命令、Key 过期淘汰、WAL 与 Snapshot 故障恢复，以及不中断集群整体服务的在线 Slot 迁移。

**项目亮点：**

1. **实现 Redis Cluster 风格的数据分片与客户端路由。** 使用 CRC16/XMODEM 将 Key 映射到 16384 个 Hash Slot，支持 Hash Tag、`MOVED`、`ASK`、`ASKING`、`CROSSSLOT` 和 `CLUSTER SLOTS` 等核心语义；将多个 Slot 聚合到少量逻辑分片，在保持稳定路由粒度的同时控制共识组数量。

2. **基于 Multi-Raft 构建强一致、高可用的数据复制层。** 每个逻辑分片对应一个三副本 Raft Group，写请求只有在日志被多数副本持久化、提交并应用后才向客户端返回成功；实现 PreVote、Leader 选举、日志复制、Leader Transfer、Learner 和 Joint Consensus 成员变更，并使用 ReadIndex 提供分片内线性一致读。

3. **设计确定性的分布式命令状态机。** 将客户端命令转换为版本化、二进制安全的规范日志格式，统一处理整数、浮点数、TTL 和对象变更；同 Slot 多 Key 写命令通过单条 Raft Entry 原子执行，跨 Slot 命令返回 `CROSSSLOT`，避免在首版中引入跨分片事务和 2PC。

4. **构建独立的元数据控制面。** 使用单独的 3/5 副本 Raft Group 强一致管理 Cluster、Node、Shard、Slot、成员配置和 Ownership Epoch；数据节点基于已提交元数据生成不可变拓扑快照，在本地完成普通请求路由，使控制面不进入数据请求热路径。

5. **实现支持故障续传的在线 Slot 迁移。** 采用“基础快照复制、增量日志追赶、源端 Fence、目标激活、元数据切换”的迁移状态机，通过 Migration ID、Ownership Epoch、状态摘要和 Raft 提交证明保证迁移幂等性与单写所有权，避免客户端双写导致的数据分叉。

6. **基于 Epoll、非阻塞 Socket 和多 Reactor 构建事件驱动网络层。** 将客户端连接固定归属到创建它的 Reactor，分片状态由 Actor 串行修改；通过连接级请求序号保证 RESP Pipeline 响应有序，并使用读写预算、有界队列和高低水位背压避免慢客户端或热点连接耗尽事件循环资源。

7. **实现五种 Redis 数据类型及自适应对象编码。** 建立统一的 `RedisObject` 模型，支持 String、Hash、List、Set 和 ZSet；Hash 可由紧凑数组升级为自研哈希表，Set 可由 `intset` 升级为字符串哈希集合，List 可由连续数组升级为双端队列，并通过双哈希表渐进式 Rehash 降低集中扩容造成的延迟抖动。

8. **实现与复制状态机一致的 Key 过期机制。** 通过 TTL 哈希索引提供 O(1) 查询，并使用有序 Deadline 索引调度最近过期任务；结合访问时懒删除和带时间、数量预算的主动删除，将过期时间和删除结果纳入 Raft 确定性执行路径，避免各副本依据本地时钟独立删除而产生状态分歧。

9. **实现 WAL、分片 Snapshot 与 Redis RDB 兼容能力。** 使用分段 WAL、批量 `fsync` 和包含 Raft Index、Term、成员配置及 Slot Epoch 的一致性 Snapshot 完成崩溃恢复；同时保留 Redis RDB v9 作为数据导入导出格式，支持 CRC64、过期元数据以及 Listpack、Ziplist、Quicklist、Intset 等官方编码。

10. **建立基础自动化验证体系。** 使用单元测试、确定性 Raft 模拟和多进程故障测试覆盖命令语义、选举复制、宕机恢复、网络分区与 Slot 迁移等核心场景。

## 二、逐条解释与面试展开

### 1. Redis Cluster 风格的数据分片与客户端路由

**这条在解决什么问题：**

单机数据库的容量和吞吐量最终受一台机器限制。数据分片的核心是根据 Key 找到唯一负责它的逻辑分片，使不同分片能够分布到不同节点并独立处理请求。

**具体如何实现：**

- 对 Key 的原始字节执行 CRC16/XMODEM，并通过 `& 0x3fff` 得到 `0～16383` 的 Slot 编号。
- 实现 Redis Hash Tag 规则，例如 `{user:42}:profile` 和 `{user:42}:orders` 使用相同的 Tag 计算 Slot，从而落入同一个分片。
- 16384 个 Slot 只是路由单元，不会创建 16384 个 Raft Group；多个 Slot 被分配给一个逻辑分片，以降低 Raft 定时器、WAL 文件和调度开销。
- 节点不是请求 Owner 时返回 `MOVED`；迁移切换窗口内返回 `ASK`，客户端发送一次性 `ASKING` 后访问目标节点；多 Key 命令涉及不同 Slot 时返回 `CROSSSLOT`。
- `CLUSTER SLOTS` 将已提交的 Slot 拓扑和可信 Leader 信息返回给 Cluster-aware 客户端，使客户端能够缓存路由并直接访问数据节点。

**面试时可以强调：**

这里兼容的是 Redis Cluster 的客户端路由语义，并没有照搬官方 Redis 的异步主从复制。内部复制采用 Raft，因此系统对已经确认的写入提供更明确的多数派持久化语义。

### 2. Multi-Raft 强一致复制

**这条在解决什么问题：**

单节点保存的数据会在进程或机器故障时不可用。Raft 将一个分片的数据复制到多个节点，并通过多数派决定可以提交的日志，从而支持自动选主和故障恢复。

**具体如何实现：**

- 每个逻辑分片对应一个独立 Raft Group，默认包含 3 个 Voter；同一进程可以承载多个 Group 的副本。
- 写请求由当前 Leader 转换为日志提案；Follower 持久化日志后响应，Leader 在多数副本持久化并提交该日志后推进状态机。
- 客户端只有在日志被提交并应用后才收到成功响应，因此单个节点故障不会丢失已经确认的写入。
- 使用 PreVote 减少网络隔离节点恢复后无意义地抬高 Term，使用 Leader Transfer 在计划下线时主动转移领导权。
- 新副本先以 Learner 身份追赶日志，再通过 Joint Consensus 安全改变 Voter 集合，避免成员变更期间出现两个互不相交的多数派。
- 读请求默认由 Leader 执行 ReadIndex，在确认当前领导权并等待本地状态机追上对应 Commit Index 后读取，提供分片内线性一致性。

**面试时可以强调：**

系统选择 CP 语义：网络分区时，只有拥有多数派的分片能够继续确认写入。失去多数派的分片宁可暂时不可用，也不会让两个 Leader 同时接受写入。

### 3. 确定性命令状态机

**这条在解决什么问题：**

Raft 只能保证所有副本按相同顺序看到日志。要让最终数据一致，还必须确保同一条日志在每个副本上产生完全相同的结果。

**具体如何实现：**

- 在进入 Raft 前完成命令名称、参数数量、整数范围、浮点数和 KeySpec 校验，将请求编码为版本化的 `CanonicalCommand`。
- 日志保存规范化命令和二进制参数，不保存原始 RESP 帧或已经编码好的响应字符串。
- 浮点数使用确定的 IEEE-754 表示，拒绝 NaN，并规范化特殊值；字符串始终以显式长度处理，保证二进制安全。
- 状态机 Apply 阶段不读取网络、本地文件、随机数或墙上时间，也不执行不可重复的外部副作用。
- 同 Slot 的多 Key 写操作封装为单条日志记录，Apply 时要么全部执行，要么全部不执行；跨 Slot 请求在路由阶段直接拒绝。
- 通过 Slot Epoch 检查日志和请求是否仍属于当前所有权世代，使旧 Leader、延迟消息和过期迁移任务确定性地失败或变成 No-op。

**面试时可以强调：**

分布式一致性不只是“实现一个 Raft 算法”。如果状态机读取本地时间、随机数或非复制配置，即使日志顺序完全一致，各副本仍然可能得到不同结果。

### 4. 元数据 Raft 控制面

**这条在解决什么问题：**

集群需要统一回答“有哪些节点、一个分片有哪些副本、每个 Slot 属于哪个分片、迁移进行到哪一步”等问题。如果这些信息只保存在单个管理节点中，管理节点就会成为单点故障。

**具体如何实现：**

- 建立独立的 Metadata Raft Group，保存 Cluster ID、Node ID、分片成员、Slot Owner、Ownership Epoch、拓扑版本和迁移状态。
- 管理操作携带幂等 Request ID，并通过期望 Revision 或 Epoch 进行 CAS 更新，避免请求重试覆盖较新的拓扑。
- 数据节点监听已提交的元数据变更，生成不可变 `TopologySnapshot` 并原子发布给各个 Reactor，普通请求只读取本地快照。
- 数据写入除了检查拓扑中的 Owner，还会检查本地 Raft Group 已持久化的 Slot Ownership 和 Epoch，避免仅凭一份可能滞后的路由缓存获得写资格。
- 控制面不参与普通 GET/SET 的请求链路。控制面暂时失去多数派时，稳定分片仍可根据最后一次已提交拓扑服务，但禁止新建分片、成员变更和发起迁移。

**面试时可以强调：**

控制面和数据面分离既减少了请求延迟，也隔离了故障。元数据强一致不意味着每个业务请求都要访问元数据集群。

### 5. 在线 Slot 迁移

**这条在解决什么问题：**

新增节点或出现数据倾斜时，需要把 Slot 从一个分片移动到另一个分片。如果简单地让客户端同时写源端和目标端，超时、重试和节点切换很容易导致两边数据顺序不一致。

**具体如何实现：**

- 控制面先创建带唯一 Migration ID、源/目标 Group 和前后 Epoch 的迁移意图。
- 源分片在确定的 Applied Index 上生成 Slot 基础快照，目标分片将数据写入对客户端不可见的 Staging 空间。
- 基础数据复制期间源端仍是唯一写 Owner；源端把快照之后已经提交的实际变更转换成增量记录，目标端通过自身 Raft 幂等应用。
- 目标追赶后，源端提交 Fence 日志，永久停止旧 Epoch 的新写，并给出由当前 Leader 线性一致查询得到的提交证明。
- 目标确认已经处理到 Fence Index、校验状态摘要一致后提交 Activate；随后源端返回 `ASK`，控制面最终将正式 Owner 切换到目标分片的新 Epoch。
- 每个阶段都持久化到相应 Raft Group，节点重启或 Leader 切换后能够从已提交状态继续；源端一旦 Fence，只允许继续向前完成迁移，不能通过超时重新开放旧 Owner。

**面试时可以强调：**

迁移安全的核心不是“把数据复制过去”，而是始终只有一个能够确认写入的 Owner。Fence、Epoch 和提交证明共同避免了双写、旧 Leader 复活和延迟消息覆盖新数据。

### 6. Epoll、多 Reactor 与 Actor 并发模型

**这条在解决什么问题：**

网络层需要同时服务大量连接，而共识状态和业务对象又不能被多个线程无序修改。该模型将网络并发与状态修改边界明确分开。

**具体如何实现：**

- Reactor 使用 Epoll 监听非阻塞 Socket，负责连接生命周期、RESP 解析和响应写回；一个连接在生命周期内固定归属一个 Reactor。
- 每个 Raft Group 作为独立 Actor，Raft 状态、WAL 顺序和 `ShardStore` 只在该 Actor 的串行上下文中修改，避免为每个对象增加复杂锁。
- Reactor 将写命令提交到对应 Group，完成结果通过线程安全队列返回原 Reactor；连接按请求序号重排结果，保证 Pipeline 响应与请求顺序一致。
- 为单轮读取字节数、命令数、执行时间和写出字节数设置预算，防止单个连接长时间占用事件循环。
- 输入、输出缓冲区设置高低水位。当下游 Raft、WAL 或客户端发送速度跟不上时暂停继续读取，从网络入口传播背压，而不是无限堆积请求。
- 客户端、Raft、Snapshot、Migration 和管理流量使用隔离的连接或资源池，保证心跳和投票不会被大快照或慢客户端阻塞。

**面试时可以强调：**

这里的“分布式分片”是 Raft 状态机和数据所有权边界。Actor 串行化使单分片逻辑更容易证明正确，不需要一开始就在复杂对象内部铺设大量细粒度锁。

### 7. Redis 对象模型与自适应编码

**这条在解决什么问题：**

不同规模的数据适合不同的底层结构。小对象如果直接使用通用哈希表会浪费大量指针和 Bucket 内存，而大对象继续使用线性数组又会使查询和更新变慢。

**具体如何实现：**

- 通过统一的 `RedisObject` 抽象保存对象类型，并在数据库层完成类型校验和 `WRONGTYPE` 返回。
- String 使用 `std::string` 保存二进制安全内容。
- 小 Hash 使用连续键值数组降低内存开销；字段数量或字符串长度超过阈值后升级为自研 Dict。
- Dict 使用链地址法解决哈希冲突，并在扩缩容时同时保留新旧两张表；每次普通操作或维护周期只迁移有限 Bucket，避免一次性 Rehash 阻塞请求。
- Set 在成员均为规范整数且规模较小时使用有序 `intset`，出现非整数成员或超过阈值后单向升级为字符串哈希集合。
- List 根据元素数量和长度从连续数组升级为双端队列；ZSet 同时维护 `member -> score` 哈希索引和 `(score, member)` 有序索引，兼顾按成员查询与按分数排序。

**面试时可以强调：**

自适应编码是在内存占用和操作复杂度之间做折中。编码升级必须保持逻辑值不变，因此 Snapshot、迁移摘要和 Raft 状态机都面向逻辑对象，而不依赖某个节点当前使用的内部编码。

### 8. 分布式 Key 过期机制

**这条在解决什么问题：**

TTL 不只是查询剩余时间。系统还要及时回收过期对象，并确保 Leader 切换、日志重放和不同节点时钟存在偏差时，各副本不会删除不同的数据。

**具体如何实现：**

- 使用 `key -> deadline` 哈希索引完成 O(1) TTL 查询，同时使用按 Deadline 排序的调度索引定位最近需要处理的 Key。
- 访问 Key 时执行懒删除，将已经到期的对象按不存在处理；后台维护周期执行带 Key 数量和运行时间预算的主动删除，避免一次清理大量 Key 阻塞前台请求。
- `SET`、`DEL`、容器删空、覆盖写和迁移操作统一维护对象与 TTL 索引，防止出现悬空 Deadline。
- 客户端设置 TTL 时，Leader 将其规范化为确定的绝对 Deadline 并写入日志；真正改变复制状态的过期删除由 Leader 通过 Raft 提交，Follower 不依据自己的本地时间独立修改状态。
- Snapshot 和迁移数据携带绝对 Deadline，恢复或迁移完成后重新构建调度索引，使故障恢复不会把过期 Key 变成永久 Key。

**面试时可以强调：**

本地时间可以用来触发 Leader 检查，但不能让每个副本自行决定状态变化。真正的删除必须进入复制日志，这样所有副本才会以相同顺序执行相同结果。

### 9. WAL、Snapshot 与 RDB

**这条在解决什么问题：**

内存数据库仍然需要在进程崩溃或机器重启后恢复数据。分布式恢复除了业务对象，还必须恢复 Raft 日志位置、成员关系和 Slot 所有权，单纯的 Redis RDB 无法承载这些信息。

**具体如何实现：**

- 每个 Raft Group 使用独立的分段 WAL，持久化日志 Entry、Term、Vote 和 Commit 相关元数据；Follower 必须先完成要求的持久化，再发送成功响应。
- 将多个日志合并为批次执行 `fsync`，减少每条写入单独刷盘的系统调用开销，同时保持多数派持久化后确认的语义。
- Snapshot 在明确的 Applied Index 上保存业务对象、TTL、Raft 成员配置、Slot Ownership、Epoch 和迁移状态；安装完成后才能安全回收被覆盖且没有迁移引用的 WAL。
- 启动时先校验 Node、Cluster 和 Group 身份，再加载 Snapshot，最后只重放 `(lastIncludedIndex, commitIndex]` 内的已提交 WAL。出现日志空洞、Term 不匹配或 Checksum 错误时 Fail-closed，不能跳过损坏记录后继续服务。
- RDB 保留为 Redis 兼容的导入导出格式，支持 Redis v9 文件头、完整长度编码、CRC64、过期元数据和多种紧凑对象编码。
- 文件落盘使用同目录临时文件，依次执行写入、文件 `fsync`、原子 `rename` 和父目录 `fsync`，避免写入失败破坏原有文件。

**面试时可以强调：**

WAL/Snapshot 和 RDB 的职责不同：前者是包含共识元数据的正式崩溃恢复机制，后者主要用于 Redis 生态兼容、离线备份和数据交换，不能直接作为 Raft 恢复点。

### 10. 自动化验证体系

**这条在解决什么问题：**

分布式系统的错误通常只在消息乱序、节点重启或网络分区等组合场景中出现，因此需要验证安全不变量，而不只是检查单次请求能否返回正确结果。

**具体如何实现：**

- 单元测试覆盖 RESP、命令语义、对象编码、TTL 索引和 RDB 兼容性。
- 确定性 Raft 模拟器控制消息投递、丢包、乱序和时钟推进，复现选举、日志覆盖与成员变更边界。
- 多进程测试覆盖节点宕机、重启恢复、网络分区、Leader 切换和迁移中断续传，并检查同一分片不会出现两个可确认写入的 Owner。

**面试时可以强调：**

## 三、一页简历压缩版

如果简历空间有限，可以使用下面的版本：

### Mini Redis｜分布式内存键值存储系统

**技术栈：** C++17、Linux、Epoll、Reactor、RESP、Raft、WAL、Snapshot、RDB

**项目介绍：**

从零实现兼容 Redis 核心协议的分布式内存数据库，支持 String、Hash、List、Set、ZSet 五种数据类型及常用 Redis 命令。系统使用 16384 个 Hash Slot 完成数据分片，通过 Multi-Raft 提供强一致复制、故障转移与水平扩展，并实现客户端路由、分布式 TTL、WAL/Snapshot 恢复和在线 Slot 迁移。

**项目亮点：**

- 基于 Epoll、非阻塞 Socket、多 Reactor 与分片 Actor 构建事件驱动服务端，通过连接预算、有界队列和高低水位背压保证公平调度，并支持 RESP Pipeline 有序响应。
- 实现 Redis Cluster 风格的 16384 Hash Slot、Hash Tag 及 `MOVED`、`ASK`、`CROSSSLOT` 路由语义，将多个 Slot 映射至逻辑分片以支持水平扩展。
- 为每个分片实现三副本 Raft Group，写请求经多数副本持久化和状态机应用后返回；支持 PreVote、Leader Transfer、Learner、Joint Consensus，并基于 ReadIndex 提供线性一致读。
- 使用独立元数据 Raft Group 管理节点、分片、Slot 所有权和 Epoch；实现“快照复制、增量追赶、源端 Fence、目标激活”的在线迁移状态机，保证迁移期间的单写所有权和故障续传。
- 实现五类 Redis 对象、自适应编码、自研 Dict 渐进式 Rehash，以及由 Raft 驱动的懒删除与主动删除 TTL 机制。
- 实现分段 WAL、批量 `fsync` 和分片 Snapshot，并保留兼容 Redis RDB v9 的数据导入导出能力；通过基础自动化与故障测试验证核心一致性语义。

## 四、使用建议

- 一页中文简历优先使用“第三部分”，保留 5～6 条亮点即可。
- “第二部分”不建议整段放进简历，可作为面试准备材料，帮助解释每条亮点的设计动机、实现方式和取舍。
- 不要填写未经实际压测得到的 QPS、P99 延迟或恢复耗时；完成压测后再用真实数据替换描述性成果。
- 分布式模块应至少完成三节点部署、Leader 故障转移、网络分区、重启恢复和迁移中断续传验证后，再以“已实现”表述。
