# Mini_Redis_cpp 仓库功能分析

> 分析日期：2026-08-25。本文依据当前 `main` 分支的源码、CMake 构建清单和已提交的构建产物整理；它描述的是当前实际接入的功能，而不是完整 Redis 的功能清单。

## 1. 项目定位

`Mini_Redis_cpp` 是一个用 C++17 编写的、面向学习的 Redis 子集实现。它提供一个监听 TCP 6379 端口的内存键值服务，能够接收 RESP 数组请求，并实现一部分 Redis 风格命令、对象编码和 RDB 快照持久化。

当前项目的设计重心是理解 Redis 的几个核心概念：

- 使用 `epoll` 的事件循环和非阻塞 socket；
- RESP（Redis Serialization Protocol）请求解析与响应编码；
- 统一的 `RedisObject` 对象模型；
- String、Hash、List、Set 与 ZSet 五种已接入数据类型；
- Hash 的小对象紧凑存储、升级为哈希表，以及渐进式 rehash；
- 将内存数据写入并从 `dump.rdb` 恢复。

它并非 Redis Server 的可替代实现：没有多数据库、过期时间、事务、发布订阅、复制、AOF、认证、Lua、集群或并发执行模型。

## 2. 实际可用功能

### 2.1 服务端与网络模型

程序入口在 `main.cpp`：创建全局 `Database` 和 `CommandHandler`，然后启动 `Server(6379)`。`Server` 使用 Linux `epoll` 等待监听 socket 与客户端 socket 的可读事件；每个客户端由一个 `Connection` 持有读、写缓冲区。

请求处理链路如下：

```text
redis-cli / RESP 客户端
        | TCP + RESP 数组
        v
Server (epoll 事件循环)
        v
Connection 读取到 read_buffer_
        v
RespParser 解析为 argv
        v
CommandHandler 分派命令
        v
Database / RedisObject
        v
RESP 响应写入 write_buffer_ 并发送给客户端
```

实现使用非阻塞 socket；读操作会循环读取直到 `EAGAIN`，写操作则尝试发送当前写缓冲区中的数据。代码层面仍是一个单线程事件循环，项目虽然链接了线程库，但没有启动工作线程。

### 2.2 RESP 协议支持

`Protocol.cpp` 的 `RespParser` 当前只接受 RESP 数组形式的请求，也就是 Redis 客户端常用的：

```text
*3\r\n$3\r\nSET\r\n$3\r\nkey\r\n$5\r\nvalue\r\n
```

它支持解析数组内的 Bulk String，并会区分“数据尚不完整”和“协议错误”。服务端可编码以下 RESP 响应：

| 响应形式 | 用途 |
| --- | --- |
| Simple String | 例如 `+OK`、`+PONG` |
| Error | `-ERR ...` |
| Integer | `:1` 等计数结果 |
| Bulk String | 读取到的字符串值 |
| Null Bulk String | key/field 不存在时的 `$-1` |
| Array | `KEYS`、List、Set 与 ZSet 范围命令使用的 Bulk String 数组 |

### 2.3 已接入命令

下表只列出 `CommandHandler::execute` 已注册并可从网络调用的命令。命令名大小写不敏感。

| 类别 | 命令 | 当前行为与限制 |
| --- | --- | --- |
| 连接 | `PING` | 始终返回 `PONG`；不支持带消息参数时回显消息的 Redis 语义。 |
| String | `SET key value` | 写入字符串并返回 `OK`。额外参数不会报错，但会被忽略；因此 `EX`、`NX`、`XX` 等选项尚未实现。 |
| String | `GET key` | key 存在且类型为 String 时返回 Bulk String；不存在时返回 null bulk string。 |
| Hash | `HSET key field value` | 新 key 会创建 Hash；类型冲突返回 `WRONGTYPE`。参数形式允许多个 field/value 对，但当前只处理第一对，且固定返回 `1`，不能反映更新或多字段写入的实际 Redis 语义。 |
| Hash | `HGET key field` | 返回字段值；key 不存在或 field 不存在时返回 null bulk string。 |
| List | `LPUSH`、`RPUSH`、`LPOP`、`RPOP`、`LINDEX`、`LRANGE`、`LLEN`、`LREM`、`LTRIM` | 支持多元素 push、负索引和范围访问；弹出或裁剪后空列表会自动删除 key。 |
| Set | `SADD`、`SREM`、`SISMEMBER`、`SMEMBERS`、`SCARD` | 小整数集合使用 `intset`；遇到非规范整数成员或超过阈值会升级为字符串集合。 |
| ZSet | `ZADD`、`ZREM`、`ZSCORE`、`ZRANGE [WITHSCORES]`、`ZRANGEBYSCORE [WITHSCORES]`、`ZRANK`、`ZCARD` | 按 score 升序、member 字典序维护顺序；支持 `+inf` 和 `-inf` score 边界。 |
| 键管理 | `DEL key [key ...]` | 删除给出的 key，返回实际删除数。 |
| 键管理 | `EXISTS key [key ...]` | 返回存在的参数 key 数。对于重复 key，会按参数逐个计数。 |
| 键管理 | `KEYS *` | 仅支持全量模式 `*`，返回所有 key；其他 glob 模式返回空数组。底层为 `unordered_map`，结果顺序不保证。 |
| 持久化 | `SAVE` | 将当前数据写到进程工作目录下的 `dump.rdb`，成功返回 `OK`。 |

## 3. 数据模型与内部实现

### 3.1 顶层数据库

`Database` 使用：

```cpp
std::unordered_map<std::string, std::shared_ptr<RedisObject>>
```

保存 key 到对象的映射。所有已接入命令均操作这个单一 DB；项目没有 `SELECT` 或命名空间隔离。数据库构造时会尝试读取当前工作目录的 `dump.rdb`，读取失败（包括文件不存在）会静默以空数据库启动。

### 3.2 String

`StringObject` 是对 `std::string` 的简单封装，是 `SET`/`GET` 使用的数据类型。`SET` 会直接创建并覆盖旧对象，因此可以将已有 Hash 覆盖成 String；相反，`HSET` 遇到已有 String 会报类型错误。

### 3.3 Hash

`HashObject` 是当前实现最完整的数据类型，采用两级编码：

| 条件 | 表示方式 |
| --- | --- |
| 小 Hash | `std::vector<std::pair<std::string, std::string>>`，代码中命名为 `ZIPLIST` |
| 字段数达到 512，或 field/value 超过 64 字节 | 提升为自定义 `Dict`，代码中命名为 `HASHTABLE` |

`Dict` 以链地址法管理 bucket。负载因子达到 1 时扩容至两倍，利用 `ht_[0]` 与 `ht_[1]` 双表进行渐进式 rehash；写入/删除期间会迁移一个 bucket，另提供按毫秒预算推进 rehash 的接口。当前服务端事件循环没有调用数据库的后台 rehash 接口，因此 rehash 主要依赖后续 Hash 写入或删除操作推进。

### 3.4 List

`ListObject` 对小列表使用 `std::vector<std::string>`，元素数量超过 512 或单个元素超过 64 字节时升级为 `std::deque<std::string>`。升级为单向操作，以保持实现简单；List 命令支持 Redis 风格的负索引与闭区间范围。

### 3.5 Set 与 intset

`SetObject` 在成员全为规范十进制 `int64` 且数量不超过 512 时使用有序 `intset`；`intset` 采用二分查找和有序 `std::vector<int64_t>`。遇到任意非整数成员、带前导零的字符串（例如 `"01"`），或数量超过阈值时，对象会升级为 `std::unordered_set<std::string>`。

### 3.6 ZSet

`ZSetObject` 同时维护 `member -> score` 的哈希索引和 `(score, member)` 的有序集合，支持更新分数、读取分数、按分数范围查询以及获取排名。

## 4. 持久化

项目实现了一个简化版 RDB 编码器/解码器：

- 数据库启动时：尝试加载 `dump.rdb`；
- 执行 `SAVE` 时：写入 `dump.rdb`；
- 收到 `SIGINT` 或 `SIGTERM` 时：信号处理函数调用 `g_db.saveRdb()` 后退出；
- 序列化 String、Hash、List、Set 和 ZSet，且只处理 DB 0；
- 文件头写为 `REDIS0009`，末尾写入 8 字节全零校验占位，不计算 CRC64；
- 长度编码仅覆盖小于 16 KiB 的字符串/长度；更大的写入会使保存失败；
- 解码器只兼容本项目使用的有限 RDB 格式，对标准 Redis 生成的复杂 RDB 文件不应假设完全兼容。

需要特别注意，RDB 文件的相对路径取决于**启动进程的当前工作目录**。例如从构建目录启动，就会在那里读写 `dump.rdb`。

## 5. 目录布局与尚未暴露的能力

项目按职责分层：

```text
include/mini_redis/  # 模块接口
  command/           # 命令分发
  core/              # 数据库、对象基类、哈希表
  net/               # RESP、连接与服务端
  objects/           # String、Hash、List、Set、ZSet
  persistence/       # RDB 编解码
src/                 # 与 include 同构的实现
tests/               # 自动化测试源码
docs/                # 项目文档
```

`Database::memory_usage()`、`get_rehashing_dicts()` 等辅助 API 尚未暴露为命令，也未由事件循环定时调度。`build/`、CMake 自动生成文件、对象文件、二进制、RDB 快照和本地测试可执行文件都是本地生成物，均由 `.gitignore` 排除，不应提交。

## 6. 当前边界与已知工程限制

除功能缺项外，下面这些限制会影响兼容性与稳定性：

1. **平台依赖**：网络事件循环直接使用 Linux `epoll` 和相关头文件。即使 CMake 写有 Linux/macOS 的说明，服务端源码本身没有 macOS `kqueue` 适配。
2. **一次只处理一个请求**：解析成功后，服务端会清空整个读缓冲区，未按已消费字节保留后续请求。因此不适合依赖请求管线化（一个 TCP 包中连续多个 RESP 命令）的客户端场景。
3. **写事件处理不完整**：客户端 fd 只注册 `EPOLLIN`。若非阻塞写返回 `EAGAIN`，剩余响应虽然保存在写缓冲区，却没有 `EPOLLOUT` 事件来保证后续继续发送。
4. **单线程且无资源控制**：没有最大客户端数、请求大小/缓冲区上限、鉴权或 ACL。
5. **命令兼容性仍是子集**：部分 Redis 选项和命令未实现，例如 `SET` 的过期/条件选项、`HSET` 多 field/value 对和 List 阻塞命令。
6. **信号处理不安全**：`signal_handler` 中调用了 iostream、RDB 文件写入和 `exit`，这些都不是严格意义上的 async-signal-safe 操作；演示用途可以理解，生产服务应改为事件循环感知退出标志后再保存。
7. **异常/错误信息有限**：RDB 读取失败会被转为空数据库，保存失败也不会向调用方给出具体原因。

## 7. 构建与试用方式

构建描述使用 CMake（最低 3.14）和 C++17，目标名为 `mini_redis_server`。在具备 Linux、CMake 与 C++17 编译器的环境中，可按以下方式构建：

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build
./build/bin/mini_redis_server
```

另开终端可用 Redis CLI 做基本验证：

```bash
redis-cli -p 6379 PING
redis-cli -p 6379 SET greeting hello
redis-cli -p 6379 GET greeting
redis-cli -p 6379 HSET user:1 name alice
redis-cli -p 6379 HGET user:1 name
redis-cli -p 6379 KEYS '*'
redis-cli -p 6379 SAVE
```

本次分析环境有 Apple Clang，但未安装 `cmake`；仓库已提交的 `build/bin/mini_redis_server` 是 Linux x86-64 ELF 产物，不能在当前 macOS/arm64 环境直接运行。因此本文完成了源码与构建清单的静态核验，未在当前环境重新构建或进行端到端命令测试。

## 8. 后续演进建议

若要继续把它发展为一个更可靠的教学型 Redis 实现，建议按以下优先级推进：

1. 修正连接层：支持连续命令解析、按实际消费长度保留缓冲区、注册 `EPOLLOUT` 并处理部分写。
2. 补齐命令语义：严格校验参数，完善 `HSET` 多 field/value 对和返回值，区分不存在与类型错误。
3. 建立测试：为 RESP 解析、命令、Hash 编码转换、RDB round-trip 和多客户端 I/O 添加单元/集成测试。
4. 完善持久化：增加原子写入、错误日志、更多长度编码与校验，并明确是否追求与官方 Redis RDB 的互操作。
5. 扩展数据类型命令：补齐 Hash 多 field/value 写入、List 阻塞命令和更多 ZSet 范围/聚合选项。
6. 加入过期时间和定时任务：这将让 `Database` 的后台 rehash 接口也有合适的调度位置。
